# IPPCIESW-668 — "EP device not ready" spam on 1-die GMEM PLDM image

- **Date:** 2026-09-14
- **Ticket:** IPPCIESW-668 (Epic, Critical, `ip-pcie-firmware-ep`, Iridium, fixVer `iridium-sw-0.1-alpha`)
- **Assignee/owner:** Yoni Izutskiver · **Reporter:** Sailaja Bandarupalli
- **Status:** Backlog / new

## Intake

- **Symptom:** ARM-FW-side log spam during boot on the **1-die GMEM PLDM image**:
  - `<err> el_pcie_ep: EP device not ready`
  - `<wrn> el_vme_runtime_gate: Failed to get PCIe revision ID, assuming VME not available`
  - `<wrn> el_pcie_ep: Failed to warm PCIe EP device-info cache: -19` (`-ENODEV`)
  - `<err> dwc_ep_ras_des: EP device not ready` → `<wrn> el_pcie_ep: Failed to enable RAS DES`
  - Repeats per app (PrimeBoot @ ~42.86s, Management @ ~42.94s). Boot still completes.
- **Where:** `ip.pcie.sw.fw.ep` (el_pcie_ep + snps_ep_ctl + dwc_ep_ras_des) + the NoC `el_vme_runtime_gate`.
- **When:** latest PO branch, regression FW `1.702.0-10092026-130619`; manifest `1.704.0-12092026 [Dirty]`.
- **Classification:** **Regression** (worked before), Palladium + `CONFIG_EL_PCIE_EP` builds.

## Root cause — CONFIRMED (code + git), mechanism LIKELY

Regression introduced by **`f2a02ed` `[IPPCIESW-443] Add PCIe EP get APIs: DevInfo, LinkInfo,
RAS-DES`** (merged 2026-09-08, in `main`; contained in FW 1.702/1.704).

All three log lines funnel through accessors that hard-gate on Zephyr `device_is_ready()`, but they
are invoked while the target device is **not yet marked ready**:

| Consumer | Call site | Gated helper | Gate |
|---|---|---|---|
| VME runtime gate | `vme_gate_is_enabled()` (`el_vme_runtime_gate.c`) → `api->get_dev_info(REVISION_ID)` | `el_pcie_ep_get_dev_info_impl` → `el_pcie_ep_get_ep_ctl_device(dev)` | `device_is_ready(dev)` (parent) **and** `device_is_ready(ep_ctl)` |
| Revision-id warm | inside `el_pcie_ep_init` (`el_pcie_ep.c:484`) | `el_pcie_ep_get_dev_info_impl(dev,…)` | same gate — parent is **mid-init**, so `device_is_ready(self)==false` |
| RAS-DES enable | `el_pcie_ep_post_bring_up_cfg()` (called from init) → `dwc_ep_ctl_ec_enable(ep_ctl,true)` | `dwc_ep_ctl_ec_enable` | `device_is_ready(ep_ctl)` |

**The regressing diff** (`el_pcie_ep.c`, warm path):
```c
-  int rev_rc = dwc_ep_ctl_get_revision_id(DEV_CFG(dev)->ep_ctl_device, &revision_id); // direct child, ungated
+  int rev_rc = el_pcie_ep_get_dev_info_impl(dev, EL_PCIE_EP_DEV_INFO_REVISION_ID, &revision_id); // gated parent wrapper
```
Pre-`f2a02ed` all three paths reached the controller through **direct, ungated child-device
pointers** (`dwc_ep_ctl_get_revision_id(ep_ctl_device,…)`; the VME gate read the cached `revision_id`
via the ungated `get_revision_id`). Direct register access does not depend on the Zephyr
`initialized` flag, so it worked during init. `f2a02ed` rerouted them through the public,
`device_is_ready`-gated API surface, which is false during the device's own (and its not-yet-run
child's) init → every call returns `-ENODEV`.

- `device_is_ready(dev)` is **definitionally false during a device's own init** (Zephyr sets
  `state->initialized` only after the init fn returns) → the warm-cache warns every boot now.
- The RAS-DES enable gates on the **ep_ctl child**; it fails because the child is not ready-marked at
  that point in the parent's bring-up.
- The VME gate is a **runtime gate** consumed before el_pcie_ep is ready → wrongly returns
  "VME not available".

**Image-specificity:** the VME-gate PCIe path is only compiled/reached on
`CONFIG_EL_PALLADIUM && CONFIG_EL_PCIE_EP` (ASIC takes `return true`). "1-die GMEM" is just the image
under test; the defect applies to Palladium PCIe-EP builds generally.

## Impact

Fail-soft (all `LOG_WRN`), boot proceeds — but silently: (1) revision-id cache never warmed,
(2) RAS-DES event counters never enabled, (3) **VME runtime gate reports VME unavailable**, gating off
VME functionality. Hence Critical.

## Fix recommendation

Separate the **internal, init-safe** access path from the **public, readiness-gated** API. Options:
1. **Lowest-risk / revert-shaped:** restore the init-time warm to the direct child call
   `dwc_ep_ctl_get_revision_id(DEV_CFG(dev)->ep_ctl_device,…)`, and call RAS-DES enable through a
   direct/internal helper that does not gate on `device_is_ready`.
2. Have the VME gate serve the **cached** revision-id (populated during bring-up while the controller
   is accessible) instead of a gated live read; keep `device_is_ready` only on the external API
   entry points, not on the internal accessors used during init/bring-up.

Owner: `ip-pcie-firmware-ep` (author Vasyl Gomonovych). The VME-gate half also lives in `ip.noc.*`
(`el_vme_runtime_gate.c`) but only consumes the EP API.

## Confidence labels

- **Confirmed:** regressing commit `f2a02ed`; the three log lines map 1:1 to its three gated call
  sites; the gate is `device_is_ready()`.
- **Likely:** the devices are unready because the calls run before ready-marking (standard Zephyr;
  not reverted-and-proven on the image).
- **Unverified:** whether `el_pcie_ep_init` returns 0 (fail-soft) vs the device staying permanently
  unready; exact per-device unready reason.

## Next experiment to confirm

Revert `f2a02ed`'s three call sites to direct/ungated child access (or drop the self
`device_is_ready` gate on the internal path), rebuild the 1-die GMEM PLDM image (`build-fw`), and
confirm the four warnings disappear and the VME gate reports available.
