# MODINFSDKSW-11515 — PCIE SEI drain interrupt during image load

**Investigation date:** 2026-08-17
**Status:** Backlog · Bug · Medium · component `ip-psoc-firmware` · assignee **Yoni Izutskiver** · reporter Dany Kiazada

## Intake
- **Symptom:** `PCIE SEI: Drain interrupt` events on the **Management port (1)**, AXI resp **SLVERR**, reason **"Drain activated due to timeout"**.
- **Where:** PCIe EP PIW MNG port; drain notify path in `el_piw.c`. FW build is **host-run** (`atl` KMD on host, revision `0x23`).
- **When:** two distinct occurrences reported (see below). No boot/functional failure — informational SEI only.
- **Repro:** not reproduced locally; two field observations on Palladium/host-FW runs.

## Two distinct drains (decoded — csr-bot)
| Report | Dir | Addr (low32) | Decodes to | Base + offset |
|---|---|---|---|---|
| Orig (Dany, 1D+GMEM load) | **Read** | `0x19da8` | **`BOOT_AND_RST_TOP.RST_MISC.RESET_IN_PROCESS`** (MNG) | `MNG_PSOC…BOOT_AND_RST_TOP_0` low `0x19000` + `RESET_IN_PROCESS` `0xda8` |
| New (Sailaja, after every FW load, host FW) | **Write** | `0x53501c` | **`MNG_SE_TOP_7_C2C_CFG_SPACE_C2C_CORE_0` + 0x1c** (C2C core config-space) | base low `0x535000` + `0x1c` |

MNG-port drain capture `addr_h` is tied 0, so only the low 32 bits are meaningful — both decode cleanly against the a1 `project_bases.h`.

## Findings

### 1. The READ drain at `0x19da8` is the *already-known-and-fixed* benign case — **confirmed**
- `0x19da8` == `RESET_IN_PROCESS`. Host-run FW polls this register over PCIe/MNG; a **hard reset** orphans the in-flight read, which drains on timeout → benign SEI. This is exactly what PR #267 ([MODINFSDKSW-4101]) suppresses.
- Suppress logic lives in `el_piw.c::el_piw_port_drain_process_cause_impl()` and fires **only** when *all* hold:
  - `CONFIG_ARCH_POSIX && CONFIG_EL_IRQ_MON` (host-run build), **and**
  - `port == MNG && trans == READ && reason == ACTIVATED`, **and**
  - `el_irq_mon_consume_post_reset(die)` returns true — the one-shot armed by `el_irq_mon_reset_cb()` on **`EL_RESET_TYPE_HARD` only** (`el_irq_mon.c:425`).
- So the read-drain is suppressed **only within the one-shot window of a hard reset**. A read-drain at `0x19da8` seen *outside* that window (e.g. during image load with no hard-reset-triggered arm, or if it drains after the one-shot was already consumed) will still be reported. → *this is why it re-surfaced despite "already fixed".*

### 2. The WRITE drain at `0x53501c` is **NOT covered by the fix** — **confirmed**
- It is a **write** to **C2C core config-space** (`MNG_SE_TOP_7_C2C_CFG_SPACE_C2C_CORE_0 + 0x1c`), on the MNG port.
- The suppress guard requires `trans_type == EL_PCIE_DRAIN_TRANS_READ`. A **write** drain can never be suppressed by the current code — it always notifies the host.
- Different register (C2C config, not RESET_IN_PROCESS) **and** different direction (write, not read) ⇒ PR #267 was never designed to catch this. Sailaja's "after every FW load" write-drain is a **genuinely new/distinct facet**, not a regression of the #267 fix.

### 3. Owning-component note
- Ticket component is `ip-psoc-firmware`, but the code that decides to suppress-vs-notify the drain is in **`ip.pcie.sw.fw.ep`** (`el_piw.c`), with the one-shot arm in **`ip.infra.sw.fw`** (`el_irq_mon.c`). The `0x53501c` target is a **C2C/scale-up** config register (`ip.se.*`). Correct owner is PCIe-EP FW (drain policy), not PSOC FW.

## Root cause (likely)
Both drains are **benign MNG-port CFG-access timeouts** — an in-flight MNG read/write is orphaned when the fabric beneath the target is torn down / not yet up during (re)load, and it drains on timeout with SLVERR. They are informational, not functional failures (Sailaja: "doesn't cause any boot/functional failures").
- `0x19da8` read: benign, and *handled* only inside the hard-reset one-shot; re-surfaces when the drain occurs outside that window.
- `0x53501c` write: benign, and *not handled at all* — the suppress path excludes writes and this non-RESET_IN_PROCESS register.

## Fix recommendation (for discussion — not yet applied)
Decide the intended policy for benign MNG CFG-access drains, then one of:
1. **Broaden the suppress window** — allow the write direction and/or the C2C-config target within the post-(hard/soft)-reset / image-load window, if these accesses are known-orphaned-by-design. Risk: over-suppression hiding a real MNG drain.
2. **Demote to log-only** for the specific benign addresses (`RESET_IN_PROCESS`, C2C core cfg) instead of a host EQ notification, so genuine drains elsewhere still notify. Lower risk.
3. **Confirm the arm coverage** — verify whether image-load actually issues a `EL_RESET_TYPE_HARD` (arms the one-shot) or a soft/warm reset (does not). If it's not hard, the read-drain at `0x19da8` will never be suppressed by today's code — that's the concrete gap for facet #1.

Before any change: reproduce and confirm which reset type the image-load path issues, and whether these MNG accesses are expected-orphaned (design) vs a real fabric-not-ready ordering bug.

## Next experiment
- Grep/trace the image-load path for the reset type it raises (`EL_RESET_TYPE_HARD` vs soft) → tells us if facet #1 is even in scope of the one-shot.
- Confirm the C2C-config write's source (who writes `C2C_CFG_SPACE + 0x1c` over MNG during load) and whether the C2C fabric is expected down at that moment.
