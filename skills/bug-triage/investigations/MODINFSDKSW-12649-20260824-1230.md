## 12649's OWN root cause — localized in code (*likely*, evidence-grounded)

Full ARM sequence (run #32180243384, FW `1.682.0-17082026-204948`):
```
*** A1 PrimeBoot FW boot DONE ***
EL_MBX - Error: ARM CPU device is NULL   (x2)
*** A1 Management FW boot DONE ***
PTUC (Power/Thermal) boot detected, starting CPU comms
CPU comms initialization started on MNG
<err> el_mmu: MMU: Got page translation error intr type:1 access:1 hop_num:5 VA:0xf3b9e000, ASID:0 AXI_ID:0x288380 INT_ID:8
<err> el_dma: el_dma_sei_isr. dma_sei.     inst=0, cause=0x8
<err> el_dma: el_dma_sei_isr. dma_d2h_sei. inst=0, resp_err_causes=0x10
<err> el_dma: el_dma_sei_isr. dma_h2d_sei. inst=0, resp_err_causes=0xa
mng:                                      (shell alive; comms never completed)
```

**Code localization (GitHub, Elmnt-Internal):**
- `"CPU comms initialization started on MNG"` → **`project.iridium.sw.fw.psoc_mng`** `src/mng_cpu_comms.c`
  — the MNG app calls `el_cpu_comms_start()` to bring up the host↔ARM mailbox (PQ/CQ/EQ) on MNG. **This is
  where 12649 stalls.**
- `el_dma_sei_isr` + `el_dma_comms_set_user_attr` ("**MMU bypass/ASID on both channels**" per the repo's
  codebase-map) → **`ip.dma.sw.fw`** `drivers/el_dma/el_dma.c`. SEI = System Error Interrupts
  (resp_error, mem_fiu, **mng_fiu**, ctrl_fiu).
- `"MMU: Got page translation error …"` → **`ip.mmu.sw.fw`** `drivers/el_mmu/el_mmu.c`.

**Mechanism (likely):** during MNG CPU-comms bring-up, a DMA transaction on the comms channel targets
**VA `0xf3b9e000` (ASID 0)** that the **MMU has no valid translation for** (`hop_num:5` = the deepest
page-walk level missed ⇒ leaf PTE not present). The MMU raises a translation-error SEI; the DMA gets an
error response (`dma_sei cause=0x8`; d2h `resp_err_causes=0x10`; h2d `0xa`). Because the comms DMA setup
fails, `el_cpu_comms_start()` never completes the channel, so the host KMD's `MBOX_INIT` (opcode 511,
msg id 0) to `PSOC_MNG_0` is never acked → `FW unresponsive` → probe `-110` → "device did not become
operational." The FW itself does **not** crash (reaches the `mng` shell) — it's a *comms-buffer mapping*
failure, not a code fault.

**Prime suspect:** a mismatch between the comms mailbox buffer address the DMA is programmed with and the
MMU mapping / ASID / MMU-bypass attribute set via `el_dma_comms_set_user_attr` — i.e. the PQ/CQ/EQ buffer
VA `0xf3b9e000` is not mapped (or wrong ASID / bypass not set) for this iridium 4die/1die Palladium config
on FW 1.682.0. Owner is **`project.iridium.sw.fw.psoc_mng`** (comms bring-up) and/or **`ip.dma.sw.fw`**
(comms user_attr / MMU-bypass) with **`ip.mmu.sw.fw`** (page tables) — **not** `compute-kmd` (12653) and
**not** `ip-se-firmware` (IPSESW-308).

**Adjacent open work (area confirmation, not the fix):** IPDMASW-166 "Handle PDMA FIU **MEM/MNG/CTRL** SEI
errors" and IPDMASW-165 (ip-dma-firmware); IPPSOCSW-976 "MUC/PTUC ops … synchronous CPU comms ack"
(ip-psoc-firmware). These harden the SEI/comms path but do not fix the underlying unmapped-VA mapping.

## IPSESW-308 family root cause (for reference — *confirmed for that ticket*, narrowed by Akshay via Lauterbach)

The ARM (PSOC/SE) FW takes a **Zephyr USAGE FAULT ("Illegal use of the EPSR", PC=0)** at boot, in
`el_se_link_init_tid` (and also, without SE, in an mbx thread). Lauterbach repro shows the CPU faults
inside the **UART/shell driver's IRQ handler**: `dev->api->fifo_read(...)` reads a **function pointer out
of the UART device struct** and jumps to it, but that pointer held **garbage (e.g. `0x12`)** → jump to
invalid PC → fault. The varying signatures (illegal EPSR / unaligned / PC=0) all trace back to the **same
UART device-struct memory corruption**. Coding-side causes (vector table, driver code, arg/thread setup)
were ruled out — the memory was already wrong when read. **Heisenbug, ~1/3 boots** — a spin-trap in
`uart_callback()` made it stop reproducing.

When the ARM FW halts on this fault, FW init never completes → host KMD `MBOX_INIT`→`PSOC_MNG_0` never
acks → `FW unresponsive` → probe `-110` → "device did not become operational." That is exactly the
12649 host-side symptom (Artur confirmed the dmesg MBOX_INIT-timeout print corresponds to this fault).

Two sub-classes (Pardha, 08-24):
1. **Crash from remote programming in the SE thread** — *worked around* by using an **SE-LPBK-enabled
   pallad image** (`..._se_lpbk` passes; `..._isr3` / plain `_w_gmem` fail — Artur's 08-24 image matrix).
2. **Crash in execution** — still under debug.

**Supersedes** the earlier "Palladium timing, not a new defect" read (Yoni, 08-17): it is a genuine
**ARM-FW-side defect** — confirmed because the **HOST FW flavor never shows it** (Andrey, 08-23), and even
a 360000 ms (6-min) mailbox timeout still never acks.
