## Run 32595599613 (08-22) deep-dive — log-grounded facts

**No device/FW reset between test tasks (confirmed).** In the edk4-z3a job log, after the first task
(`vLLM ... power_on_tests`) booted cleanly (`[0s] fw_boot_sts=done`), every one of the next ~20 tasks
does *only*: re-`Detected Palladium device (revision: 0x23)` → `Loading el_pci`/`el_ctl`/`el_accel` →
`Waiting for device to become operational` → `ERROR` (~2 min). **19×** in the one job. There is **no**
`pd_load`, power-cycle, reboot, FW reload, or device reset anywhere between tasks — the harness only
reloads the host KMD drivers. So one wedge after task 1 poisons the entire ~3 h job; a 2nd `vLLM`
attempt at 22:46 also failed. *This is why it "spans 3 hours for all subsequent tests."*

**Device stays PRESENT throughout.** Each task re-reads `revision: 0x23` off the bus — it's not a
link-down/device-disappear; the device enumerates but the FW never re-signals operational.

**`el_pci` load is pathologically slow (~6 min each task).** `Loading el_pci` → `Loading el_ctl` gap is
consistently ~6.5 min (e.g. 20:40:38 → 20:46:46). Same thing that surfaced on 08-21 as
`task modprobe blocked for more than 122 s (elp_init [el_pci])`. `elp_init` is stuck waiting on the
device FW-boot handshake, then the device still isn't operational.

**NOT one station — it's z3a-zone-scoped (confirmed).** Device-not-operational occurrences per station
in this single run:

## First-reported occurrence (run 32412352255, 08-20, edk4-z3a) — origin analysis

**Apply reasonable doubt: "did not become operational" is a generic symptom; the 08-20 origin looks
*different* from the 08-22 one, so don't assume one root cause.**

- **08-20 (original report):** the *first* task (`vLLM … power_on_tests`) polled `fw_boot_sts` and got
  `0x1` (in_progress) **from the very first sample** (`[20s]`) and it stayed `0x1` for the full 1200 s →
  timeout. **The FW never booted at all in this job.**
- **08-22:** the first task booted cleanly (`[0s] fw_boot_sts=done`); the wedge appeared only *after*
  task 1, mid-job. Different failure mode → plausibly a **different origin**, same no-reset cascade.

**What executed before the first failure, within the 08-20 job:** only runner setup, artifact extract,
`git reset --hard HEAD` (checkout), then the vLLM task's own `venv`/`pip install` (the `--download-models`
part). **No device interaction, no design load, no `pd_load`, no reset/power-cycle anywhere in the job**
(only "host_fw_enable is not set to 1, skipping fwemu driver"). Artifact pins here: `psoc-fw-ci`
**1.683.0**, `project-iridium-sw-csr-ci` **1.35.0** (HB fix present).

**Structural conclusion (confirmed):** the regression harness **attaches to an already-loaded, already-
running Palladium design** (image_id 35, `mc_z3a_1rack_1sop_1die_w_gmem_isr3`) — it never loads or resets
the design at job start. So on 08-20 the FW was **already stuck at `fw_boot_sts=0x1` before the job
attached**. The wedge **did not originate in the reported job** — it was inherited from whatever ran on
`pldm-edk4-z3a` (a prior job, or the out-of-band design load itself) *before* 20:41. The ticket's "first
report" is just the first regression job to attach to an already-wedged design.

**Therefore the real "point it was first reported" is upstream of this job.** Next step: identify what ran
on `pldm-edk4-z3a` before 20:41 on 08-20 (previous job on that runner / the design-load/bring-up event) —
that is where the FW first failed to complete boot. The host KMD log can't show it; the **PSOC FW-side
console** from that earlier window is needed.

## Multi-station & historical scope — z3a-zone bring-up fragility

**08-20 origin run: z3a-wide, inherited-at-attach.** All analyzable z3a stations were wedged from the
first `fw_boot_sts` sample (`in_progress 0x1`, `wait_fw_boot_sts timed out`): edk4-z3a (19 not-op),
edk5-z3a (1), edk6-z3a (3), edk0-z3a (probe-stage). **Zero z2a** stations showed the boot-wedge (their
Test-step failures are unrelated tests). 4 independent runners can't be wedged simultaneously by chance →
**shared z3a cause** = the z3a design/image bring-up (`mc_z3a_1rack_1sop_1die_w_gmem_isr3`, image_id 35),
not a per-runner prior job.

**Recurring near-nightly on edk4-z3a, with *different* sub-signatures** (reasonable-doubt reinforcement —
these are likely not one root cause but z3a bring-up fragility surfacing variably):

**Where the origin actually is (and why GitHub can't show it):** the wedge is present *before* the
regression job attaches, and the harness never loads/resets the design. So the first-boot failure happens
in the **emulation design-load / PSOC primeboot** path on the z3a station — visible only in the PLDM
station's `pd_load` + **PSOC FW-side UART/console**, not in any GitHub Actions log. That is the required
next artifact.
