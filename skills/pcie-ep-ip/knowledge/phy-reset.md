# PHY Reset Signal Chain

- **Recorded:** 2026-10-27 (FW behavior added; RTL findings retained)
- **Status:** Verified from RTL + A1 FW driver
- **Tags:** phy reset, perst, hot reset, phy_perst_n, phy_rst_n, psoc reset, fw sram copy, clkrst

## Scope / Question

Which reset events reach the PCIe6 PHY, what each PHY reset signal drives, and how PERST vs
Hot reset differ (including FW SRAM impact), plus PSOC reset-manager mapping.

## Findings

Two distinct PHY reset signals, both generated by Synopsys `DWC_pcie_clkrst.v` inside `pep_wrap.v`:

### Inputs to controller reset block (from PSOC via `pcie_ep_cls.v`)
- `perst_n` ← `async_psoc2pep_perst_n` — PERST from PSOC reset manager (or external GPIO pad)
- `power_up_rst_n` / `button_rst_n` ← `async_pep_rst_n` — cold/power-on reset from PSOC

### Outputs from controller to PPW
| Signal | Asserted on | Drives in PPW |
|--------|------------|---------------|
| `phy_perst_n` | Cold reset, Warm reset, **PERST** | `phy_reset` (= `~phy_perst_n`), APB `presetn`, JTAG `trstn`, SRAM `rst_n` |
| `phy_rst_n` | Cold reset, Warm reset, **PERST**, **Hot reset** | Per-lane `pipe_laneX_reset_n` |

### Key facts
- **PERST asserts both `phy_perst_n` and `phy_rst_n`** — full PHY reset including FW SRAM wipe
- **Hot reset only asserts `phy_rst_n`** — PIPE lane reset only, no PHY core/FW/SRAM impact
- FLR, platform, WD, hard, soft, debug resets do NOT reach the PHY at all
- After PERST, PIW `fw_sram_copy_handler` automatically re-copies FW from PIW SRAM → PHY SRAM
  (FSM in `piw_macro/rtl/fw_sram_copy_handler.v`)

### PSOC reset manager mapping (from `ip.psoc.rtl`)
- PSOC has 9 reset types → 129 unit reset outputs
- PCIe units = `async_pcie_rst_n[1:0]` (unit indices 16-17)
- `async_prstn` (PERST output) can be sourced from either unit_rst[16] or external GPIO pad (CSR selectable)
- Only **POR** and **warm reset** types assert PCIe unit resets by default
- Hot/FLR flow goes FROM PCIe TO PSOC (`async_pcie2psoc_hot_rst_n`, `async_pcie2psoc_flr_rst_n`),
  not the other way

### A1 firmware behavior
- FW does **not** directly drive `phy_perst_n` or `phy_rst_n`; those are RTL-generated reset
  outputs. The EP driver observes PERSTn deassertion and warm-reset-manager phases, then invokes
  post-reset bring-up (`el_pcie_ep_reset_perstn_deasserted`,
  `el_pcie_ep_reset_callback`, `el_pcie_ep_reset_run_post_reset`).
- Link bring-up redistributes PHY FW to the PHY CCMs when needed
  (`el_pcie_ep_do_linkup`, `el_pcie_ep_phy_fw_deploy`). The PIW SRAM stage is POR-only and
  retained across resets (`el_pcie_ep_do_phy_fw_stage`).
- After hot reset, FW treats the PHY FW as resident and skips reloading it; after resets that
  clear PHY CCMs, FW redistributes the retained PIW SRAM image and restarts the PHY CPU.

## A2 UPDATE (2026-11-09, Neo against A2 RTL/CSR)
A2 has no FW-writable PHY reset; PHY reset follows `phy_perst_n`. See [a2-phy-cpu-start-and-copy-fsm.md](a2-phy-cpu-start-and-copy-fsm.md).
