# Review Memoir

Personal notes on code review style, conventions, and design approaches.
Grows with each review — captures what I look for, recurring patterns, and lessons learned.

---

## Review Philosophy

- **Correctness first, style second.** Only flag style if it actively hurts readability or maintainability.
- **Actionable comments.** Every comment should say *what* to change and *why*. No drive-by "hmm" comments.
- **Pick battles.** 3 well-reasoned blockers > 15 nits. Author energy is finite.
- **Respect the author's design.** Don't redesign in review unless there's a clear defect or scaling problem.
- **Verify claims.** When a comment says "this is safe because X" — verify X. Read the actual code path.
- **NEVER submit a verdict or post comments to GitHub without an explicit "submit" / "post it" instruction from the user.** "Resolve this", "next item", "good", or "LGTM" from the user are not submission instructions — they are conversational. Stop at presenting the draft and wait for an unambiguous directive.

## What I Always Check

### Concurrency & Synchronization
- A sampled readiness boolean cannot preserve a reset transition that closes and reopens between polls. Verify runtime callers of init/finalization before accepting a boot-only rationale; when the CPU survives reset, use transition-driven invalidation or an epoch for retained snapshots.
- Mutex scope: is the critical section minimal? Does it cover both read and write of shared state?
- Semaphore semantics: binary vs counting, take/give balance, timeout handling.
- Monotonic state flags read outside mutex: safe only if transition is one-way (false→true).
- Memory ordering: on multi-core shared memory, look for barriers/volatile.

### Error Handling
- All error paths must release held resources (mutex, allocated memory, semaphore).
- Error codes should be meaningful — propagate specific errno, don't collapse to -1.
- Validate at system boundaries (public API), trust within internal helpers.
- An error branch that returns/absorbs silently deserves a `LOG_WRN`. A handler that swallows a real failure (bad args, unexpected state) with only a comment explaining it leaves nothing in the log when it fires in the field. Cheap nit, high debug value — worth the one line whenever the branch is genuinely abnormal (not just a spurious/expected no-op).

### Hardware Programming
- Register names are not severity contracts: combined status views can include correctable causes and live non-error state under an "uncorrectable" name. Check every monitored field against the classification mask, not merely whether an existing raw dump reads the same register.
- When a flow switches transport/backends mid-sequence, verify the proof that the prerequisite link/path is already up and look for an immediate sanity read after the switch.
- **Splitting a public HW-enable API into a `_public` wrapper (keeps `device_is_ready` + `LOG_ERR`) and an `_internal` variant (drops the readiness check) is a legitimate pattern when the enable must also run from inside the device's own `*_init` — `device_is_ready(dev)` is still false during init, so calling the public API there would always `-ENODEV`. Don't flag the dropped check as a regression; verify instead that the internal path keeps the *other* guards (ownership/`owned_check`) and that reset-survival is covered elsewhere.** A register block cleared by hot/PERSTn reset must be re-programmed on the reset re-arm path (e.g. a `post_bring_up_cfg` invoked from the reset handler), not only at cold init — confirm the reset path re-invokes the enable before approving a "enable at init" change.
- **A "restore state in the parent's init, self-gate in each child's init" design depends on a parent-inits-before-children invariant — audit every board's INIT_PRIORITY overrides against it, not just the driver code.** When a parent device restores persisted state (ownership, mode) in its init and children read that state during *their own* init to decide how to configure (e.g. leave an interrupt line disabled), the scheme silently breaks if a child inits first: the child reads the not-yet-restored state and configures itself wrong. The driver logic can be perfectly correct while a *board* `.conf` breaks it two ways — (a) it bumps the parent's `*_INIT_PRIORITY` late (emulation/PHY-availability reasons) but leaves a child at its default low number, inverting the order; (b) two devices sit at the *same* priority in one init level, so order is link-order, not guaranteed. The fix lives in the board Kconfig (every child strictly after the parent), not the driver — so grep all `*_INIT_PRIORITY` overrides across boards and confirm each child sorts after its parent. A child whose own init does essentially nothing but connect+enable its IRQ line is the classic victim. Frame as a question to the author (was the child's priority simply missed when the parent's was moved?) rather than a driver defect.
- **A newly-added "warn + clamp" guard must be checked against the *expected* path, not just the broken one.** When a round-N blocker ("nothing validates that this base/size/offset is aligned to that aperture") is answered with a helper that logs a warning and then masks the value to what HW would decode anyway, the fix is usually correct — but re-derive which call sites now hit the warning on a normal boot. The classic shape: one call site genuinely needed the clamp, while a second site feeds a value whose masked result is *identical to what it already was*, so the clamp is a no-op and the warning is pure recurring noise (multiplied by ports × dies, it can be a dozen scary lines per boot). Two findings fall out: restrict the loop to the site that needs it, and don't warn when the masked value equals the original. A warning that fires on the intended path trains people to ignore the log — that's a real finding, not a nit.

### API Design
- Before asking code to restore prior global state, confirm the intended steady-state policy. A sticky post-init mode is a design contract, not a state-leak bug.

### DTS / Device Tree
- Required vs optional properties: does the binding match actual usage?
- Phandle ownership: which node logically "owns" a reference? (SE owns topology, not individual C2C ports.)
- Table size assertions: BUILD_ASSERT that DTS arrays don't exceed HW limits.
- Properties on a binding must describe *that device*. Integration glue (wrapper hardware, sibling-block regs) belongs in its own binding with a phandle, not as add-on properties on the vendor device node.
- **`DT_NODELABEL(specific_node)` inside a per-instance `DT_INST_FOREACH` body is an instance-routing bug.** A driver loop that hardcodes one integration node label (e.g. `piw0_sei_root`) wires *every* instance to instance 0's resource — silent misrouting the moment a second instance is enabled, no compile error. It also bakes an integration-layer (proj_infra) node name into IP-repo code, so a product that names its nodes differently won't link. Resolve the target structurally from the device node (walk the candidate nodes, match the one whose phandle points at *this* instance) instead of a global label.
- **A mutual phandle (A→B and B→A) is a devicetree cycle that fails the build.** edtlib adds a graph edge for every phandle/phandle-array property; if B already references A, you cannot add an A→B phandle to invert the lookup — `gen_defines.py` hard-errors with "cycle in devicetree involving …". To carry the reverse association, put a *scalar* discriminator on the side that already holds the phandle and match structurally; never a back-phandle.
- **In a multi-repo feature split, a SoC-DTS PR defines device + IRQ-tree nodes (all `status = "disabled"`) that a *separate* board PR enables — grep whether every defined node is actually enabled somewhere.** A board that wires only half the defined nodes (e.g. the PIW/EP half but not the PPW half) leaves the rest as dead, unactivated plumbing. When the enabling overlay carries a comment claiming it wires *both* halves, that comment↔reality mismatch is the finding — either enable the missing half or narrow the comment. Check the `CONFIG_*` twin too: the driver Kconfig for the unwired half will have no `=y` anywhere (same family as the no-op-gate/second-consumer checks). The SoC-DTS PR that only *defines* the nodes is still clean — the coverage gap is the consuming board's.
- **A tree/topology whose nodes reference a `device = <&devN>` phandle imposes a *bidirectional* device⟺node invariant: an enabled node whose device is disabled fails the build (`__device_dts_ord_N undeclared`), and a disabled node is always safe. So the audit runs both ways — for every board that enables the nodes, confirm all referenced devices are `okay`; for every board that *drops* a device, confirm it also disables that device's nodes.** The clean authoring pattern is a matched pair of include-able overlay helpers (`_enable.dtsi` / `_disable.dtsi`) that toggle the *exact same* node label set, plus an `_enable_all.dtsi` wrapper so a board can't end up with N-1 of N trees live. Reviewer checks: (a) the helper's node list is identical between enable and disable and matches the inst-template's node set one-for-one (a node added to the template but not the helpers is silently never toggled); (b) each board that includes `enable_all` has every referenced device instantiated; (c) the one variant that drops a port uses the `_disable` helper for exactly that port. When all three hold it's a clean approve — the helper pair *is* the footgun guard.
- **A DTS-only enablement PR that adds `interrupt-names` (or any property a driver gates on via `DT_INST_IRQ_HAS_NAME`/`DT_INST_PROP`+`COND_CODE_1`) is the trigger that flips the driver's guarded arm from the empty branch to the live branch — review the driver code that arm emits, not just the DTS.** The DTS PR looks trivial (just node properties) but it's precisely what activates latent driver code that no build previously compiled (the classic "macro-as-bare-value" / dead-`IRQ_CONNECT`-arm family). Before approving the enablement, confirm the driver's true-arm is already landed and correct on the base branch (grep the `COND_CODE_1(DT_INST_IRQ_HAS_NAME(...), (live-arm), ())` and read the live-arm), and that CI actually builds a board carrying the new properties — a green build on the enabling board is the real proof the driver arm compiles.
- **A "make X opt-in" refactor that flips shared DT nodes from implicit-`okay` to `status="disabled"` + an `_enable_all` helper has one regression to hunt: a board that *previously consumed* the nodes but doesn't now opt back in. The consuming set is the intersection `device-enabled ∧ walker/consumer-CONFIG-enabled`, not just `device-enabled`.** Grep every overlay that enables the referenced device (e.g. `&pcie_ep_piw0`), then filter to those whose `.conf` also enables the code that *reads* the nodes (`CONFIG_EL_IRQ_TREE` walker, etc.). A board that enables the device but not the walker never consumed the nodes — disabling-by-default there is **inert, not a regression** (drop the finding). Only a board in the intersection that fails to include the new helper is a real coverage loss. Confirm the walker Kconfig is `default n` with no `select` from a sibling symbol before assuming "IRQ_MON implies IRQ_TREE."
- **A touched *base* board overlay silently reaches every die-count/product variant that layers on it — even when the variant `.overlay` has no `#include` of the base.** In repos where `el_<x>_palladium_aw_dual_die` builds = base `el_<x>_palladium.overlay` + variant delta (the variant is a small delta that doesn't re-enable the shared devices, yet the variant *build* has them `okay`), an enable added to the base propagates to the variants. So "this enable lands on a board with no walker" can be a false positive: the same base overlay is consumed by a variant whose `.conf` *does* enable the walker. Verify walker reach on the variant, not just the plain board — confirm via the variant's generated `build/.../zephyr.dts.pre` (does it carry the base-overlay content?) rather than assuming independence. The matched-helper node-set symmetry check (defined = disabled = enabled, one-for-one) still stands as the primary correctness gate for the DTS PR itself.
- **A numeric id property on a selectable node, when a phandle already binds it, usually only serves a runtime-select API — prefer a `name` string.** When each variant node (connection scheme, profile, mode) carries a `foo-id = <N>` *and* the parent references the default by phandle, trace where the id is actually consumed: the default binding already works off the phandle (the driver dereferencing id→linear-search back to the phandled node is a redundant round-trip), so the id's only real job is the caller-facing select API + shell display. A **name string** (`scheme-name = "ocean"`) beats an artificial `A/B/C`/numeric id there — self-documenting, matches real-world vocabulary (the data often already has names, e.g. generated from `ocean/aqua` CSVs), drops any `enum`↔`#define` hand-sync between the public header and the DT header, and is how a real producer selects. Keep the default a phandle; use a custom `*-name` (not the reserved `label`); define match semantics (`-ENOENT` + list-available on miss). The swap is a self-contained readability win independent of whether the runtime-select producer exists yet.
- **A board-overlay connection/topology table whose header comment enumerates the *full* physical wiring while the table programs only a *subset* is a comment↔table mismatch — but decode the table against the driver's filter before deciding blocker vs question.** For a packed N-tuple `connections` array (e.g. SE `<tray src-dev dst-dev role phys-port>`), the FW runs on every node and keeps only rows where `src-device == this device` (see `el_se_build_conn_map`). So a 2-chip board listing one `RP` row + one `EP` row is *one* bidirectional link (each end configures its own port), even when the comment lists all 7 possible port pairings. On an emulation/palladium board this minimal single-link set is often intentional (emulator capacity) — classify as a **QUESTION** ("minimal palladium set intended? add a one-line note") not a blocker, especially when a sibling board (8c) programs the full mesh and this one doesn't. The clearer sub-finding is an internally self-contradictory comment: "direct C2C (no switch), all 8 ports" over a table that uses `EL_SE_DST_SWITCH` on port 7 and leaves ports 1-6 unconfigured — reconcile prose with the rows.
- **Before flagging an asymmetry between sibling *app* repos carrying the same board revision, check each app's own existing overlays for its convention.** Two apps (e.g. `psoc_mng` vs `psoc_primeboot`) can legitimately differ for the same board: one includes an IRQ-tree-disable helper for a dropped port, the other omits it — and that's correct if the second app omits that helper in *all* its overlays (it doesn't instantiate that per-port tree at all). Grep the app's whole `boards/` dir (including the already-merged siblings like 8c) before calling the new board's omission a bug; the new revision mirroring the app's existing pattern is the tell it's fine.

### Test Infrastructure Segregation
- For any PR that adds test/diagnostic infrastructure (shell commands, record buffers, injection APIs, instrumentation), ask explicitly: *is the test logic cleanly segregated from the production path?* Gating tends to be partial — a single `CONFIG_*_TEST` may guard the shell command but leave the supporting record-keeping, inject API, or scratch state living unconditionally in the production driver / ISR. Audit every test-only helper, struct, and API for its real gate, not just the user-facing command.
- **A feature PR that quietly flips a test-infra Kconfig `default` from opt-in to on-by-default is scope creep with a production blast radius — check the enabling parent's own default before waving it through.** A `default n` (or `default y if ARCH_POSIX`) → bare `default y` change on a test/shell/record-buffer symbol lands the scaffolding on every build whose *parent* gate is already on. If the test symbol `depends on <shell>` and that shell is itself `default y`, the flip reaches real-silicon builds — while the help text still says "Disable in production." The tell: the default change is unrelated to the PR's stated feature (the feature compiles fine either way). Flag as a question — is the flip intended, does the test infra belong on silicon by default, and would `default y if ARCH_POSIX` preserve the prior production-off posture?

### Code-Move / Refactor PRs
- Hash-compare the moved blobs (pre-move source vs post-move destination) — byte-identical is the gold standard, not visual diff. Use the cleanup-commit's parent in the source repo, not its main tip (which still has the files).
- Pull the canonical commit list from `gh pr view --json commits` — `git log origin/main..HEAD` may include sibling PRs' commits queued behind this one.
- For "unreferenced" deletion claims, filter grep results for three recurring false-positive classes: (a) peer files in the same bundle referencing each other, (b) built-artifact snapshots that self-reference, (c) commented-out blocks in build files.
- Anchor or word-boundary substring greps (`expect_sc` matches `expect_scan`; `dirty_check` matches commented cmake) — otherwise you re-investigate non-issues.
- **Always re-read the final PR diff right before posting.** Squash/force-push or revert during the review window can erase code your findings target. Snapshot once with `gh pr diff <N>` and audit each parked finding against that snapshot.
- **On any function rename, word-boundary grep for the old name across `.c`/`.h`.** Function-pointer table entries (`.op = old_name,`) and forward declarations escape IDE refactors and only fail at link time — which never happens if no CI config builds the affected TU.

### Re-review / Verdict Gating
- **The GitHub thread `isResolved` flag is unreliable — verify every UNRESOLVED thread against the current head before deciding.** Authors routinely fix a comment in code but never click "resolve", so a re-review split of "N resolved / M unresolved" over-counts open work. Grep the exact code region each unresolved thread points at on the new head; an untouched-but-marked-resolved thread is the rarer risk, but a fixed-but-still-unresolved thread is common and will make you wrongly withhold approval. Decide on the code, not the flag.
- **Before approving, confirm the *heavy* CI (build+lint) actually ran on the current head — not just lightweight validators.** In repos where CI only fires on `/ci` or on review-approval, `gh pr checks` can show pr-validate/forbidden-words green while `ci_start`/`lint_done` say "CI not run yet". A prior round that was RED on build/lint is not cleared by a rebase alone; trigger CI and confirm green on the exact head before (or as part of) approving.
- **A multi-PR review task is `done` only when *every* PR merges; approving one member PR keeps the task in-progress.** Update just that PR's review-status to `approved` (`review-update <id> approved --pr <N>`) and leave the sibling PRs (often first-review, never looked at) tracked — don't close the task on a single approval.
- **A prior-round rename that updated the declaration/definition but not every call site leaves latent undefined-symbol build breaks behind config gates — and a later PR that fixes *some* of the dangling callers "in passing" is the tell to grep for the rest.** When a diff swaps `old_fn`→`new_fn` at one call site unrelated to its stated purpose, grep the whole repo for `old_fn`: if it has no definition anywhere and other `CONFIG_*`-gated files still call it, each of those is unbuildable the moment its config is `=y` (green CI just isn't building that config). Insist the cleanup fixes all dangling callers or none — a half-applied rename fix leaves the tree in a worse, inconsistent state than before.
- **Confirm at least one in-tree CI target actually compiles the changed code with the relevant `CONFIG_X=y`.** Green CI on a PR whose touched code is gated by a flag no twister/sample/test enables proves nothing — check the build coverage before trusting the checkmarks.
- **Where approval is itself the CI trigger, approving does not guarantee CI ran — re-check the checks afterward.** The `trigger-ci` job has its own preconditions (commonly "does the PR have all required reviewers"), and it can fail them, leaving `ci_start`/`lint_done` still red at "CI not run yet". `ci_start = SUCCESS` is the only proof CI actually launched; `trigger-ci = FAILURE` means your approval was consumed and nothing was built, so the PR needs additional approvers before any build/lint evidence can exist at all. Always re-read `gh pr checks` after approving rather than assuming the approval cleared the gate you approved despite.

## Recurring Patterns (Firmware)

### Shadow + Program pattern
- Shadow tables hold the source of truth for write-only HW registers.
- `seed()` populates shadow under mutex; `program()` writes to HW under mutex.
- Single-entry writes (`write_npa_entry`) update shadow AND program HW if already programmed.
- Thread-safe: all shadow access protected by the same mutex.

### Init Thread with MW Handshake
- Dedicated thread waits for middleware signal (semaphore).
- Timeout → DTS fallback. No timeout → wait forever (production flow).
- After seed (either MW or DTS), program HW and signal "done".
- Callers (e.g., link-up path) use `wait_ready()` to block until LUT is programmed.

### Validation-then-mutate
- Validate ALL inputs before modifying any state.
- Return error early if invalid — no partial state corruption.
- Use bitmask tracking (seen_mask) to detect duplicates and gaps in table indices.

## Design Approaches I Approve Of

- **Kconfig `choice` for N source files exporting one symbol:** When several `.c` files each define the same array/symbol (e.g. per-variant firmware blobs) and exactly one must be linked, a `choice` (with a `default`) makes mutual exclusion a compile-time guarantee — no duplicate-symbol link error, no doubled footprint, and a self-documenting single-select. Prefer over independent `bool`s that rely on board configs never enabling two.
- **Enum duplication with BUILD_ASSERT:** Public enum (el_se.h) mirrors internal enum (c2c_lut.h) with compile-time assertion that values match. Avoids exposing internal header to external consumers.
- **DT_INST_FOREACH pattern for device arrays:** Builds static const device pointer arrays at compile time. Clean and zero-cost at runtime.
- **Topology presets from DTS:** Compile-time struct array initialized from DTS node labels. No runtime parsing, no dynamic allocation.
- **`c2c_lut_wait_ready()` take-then-give:** Allows multiple callers to "pass through" a one-shot semaphore. First caller blocks until signal; subsequent callers immediately succeed because the sem is given back.
- **Single-source-of-truth header for deliberately-suppressed interrupt cause bits.** One header defines each suppression as `SUPPRESS_<REG>__<ENTRY>` macros ORed into a per-register aggregate, and that one value feeds *every* consumer of the register — the HW MASK reg (ARM interrupt path), the `el_irq_tree` `ignore_mask` (host poll path, since MASK only gates the CPU line while CAUSE still latches and gets polled), and the irq-test skip list. Prevents a bit being suppressed in one path but left live in another. Good self-imposed rules to look for: each entry carries an explicit reason tag (ERRATA / BY-DESIGN / PLATFORM), a ticket, and a stated removal criterion; values use generated `_MSK` field macros (bit positions move between IP revisions), never hex. **Reviewer audit: verify the header's own rules actually hold for every entry** — an entry missing its tag/removal-criterion, or a `PLATFORM`-tagged ("not present in silicon") entry compiled *unconditionally* (so it suppresses on real silicon too, not just emulation), is the finding. Once the framework supports per-entry Kconfig gating, a platform/emulation-only suppression should be gated (`default y if ARCH_POSIX`), not hard-compiled.

## Anti-patterns I Flag

- **`#if 0` blocks in production code.** Use Kconfig or remove entirely. Dead code rots.
- **Disabling code by commenting out its calls orphans the surrounding scaffolding.** When a feature is turned off by commenting out its call(s) rather than removing them, two things rot: (a) the descriptive comment above it keeps describing behavior the code no longer performs — actively misleading to the next reader who trusts the prose; and (b) an `#include` added solely for that now-commented call becomes a dead include. If the disable is temporary and tracked, keep only a short `/* [TICKET-ID] TODO */`, drop the stale descriptive prose and the orphaned include — git history preserves the scaffolding for the eventual re-enable.
- **Static `bool table_logged` to suppress repeated logs.** Hides bugs. Use LOG_DBG with Kconfig level control instead.
- **Per-instance data that's actually global.** If all ports share the same LUT tables, model it as global state (like this PR correctly does) not per-device config.
- **Casting between structurally-identical but separately-defined structs** (`el_se_chip_info*` → `c2c_chip_info*`). Safe only if layout is guaranteed identical. Prefer BUILD_ASSERT on sizeof and offsetof, or use a single definition.
- **Comments that justify a design by pointing at a sibling source file.** `/* mirroring el_c2c.c */`, `/* same pattern as foo.c */` — the reference rots the moment the cited file is refactored, renamed, or moved to another repo, and it forces the next reader to go read an unrelated driver to understand this one. State the reason directly ("registered on the poll walker so no DTS phandle is needed"); if the cross-file precedent genuinely matters, it belongs in a design doc, not an inline comment. Grep the whole PR for the cited filename — this kind of reference is usually copy-pasted into more than one file, and commenting on one instance leaves the others.
- **Stale in-tree dev/migration docs.** In-tree developer notes (`TODO_*.md`, `*_migration.md`, AI-review helpers) are not inherently bad — they're a legitimate way to capture context. The anti-pattern is *staleness*: a doc describing a one-shot migration that already happened, a helper file scoped to a single PR's review, or descriptions that no longer match the code. Flag when content is stale, scoped to a closed event, or misleading; accept when the doc describes ongoing usage or current design. Ask: "does this still serve a future reader?"
- **A "skip this step here, we do it elsewhere" fix can silently kill a Kconfig option — check which layer owned the gate.** The typical shape: a wrapper function honors `CONFIG_X` (real body vs no-op stub) while the alternate/deferred path calls the underlying API directly. When a commit gates off the call that went through the wrapper, `CONFIG_X=n` stops having any effect on that board, and the option reads like it still works. On any diff that defers or disables a call, trace whether the surviving path still passes through the config-gated wrapper.
- **Deferring init work to a later init level moves it to cold boot only — ask what re-runs it after reset.** `SYS_INIT`-style hooks fire once per power-on, so a step relocated out of a device's own init silently drops off any warm-reset/re-bring-up path that re-enters the driver through a different entry point. Trace the reset path explicitly: if it calls `bring_up()`/`post_bring_up_cfg()` but never the original start/init function, the relocated step is never re-applied. Note that this is often *pre-existing* rather than newly broken — but a PR that makes the step succeed for the first time is what makes the gap live, and that's the moment to raise it.


## Lessons Learned

Consolidated by theme. Each bullet is a distilled, reusable rule; review-specific
provenance is dropped in favor of the principle.

### Snapshot Discipline (before you post)
- **In local-workspace mode, verify a suspected syntax/build "blocker" against the PR head (origin) before flagging it.** A transient uncommitted edit in your own working tree can masquerade as the author's defect — `py_compile`/build failing locally proves nothing if `git diff origin/<branch> -- <file>` is empty or the origin blob is clean. Diff the touched file against the remote head before drafting any "this doesn't compile / import" finding, and drop it (don't just skip) once it's shown to be a local artifact — the CI-is-green corollary it implied dies with it.
- **Always re-pull the final PR diff right before drafting and again before posting.** Subagent file-stat estimates and early `gh pr view --json files` snapshots include intermediate-commit churn that later gets squashed, reverted, or force-pushed away. Findings die silently when they target code that isn't in the final diff. Snapshot once with `gh pr diff <N>` and audit each parked finding against that snapshot.
- **Pull the canonical commit list from `gh pr view --json commits` and the canonical diff from `gh pr diff`.** `git log origin/main..HEAD` and `git diff origin/main..HEAD` may include sibling PRs' commits queued behind this branch (dependency chains, merge queue). A local-diff file that doesn't appear in `gh pr diff` is a queued-sibling artifact, not scope creep on this PR — drop it before drafting. This bites on any PR with a stacked-branch workflow, not just multi-repo refactors.
- **`grep BUILD_ASSERT` (and existing assertions) across the PR's files before flagging a missing one.** Compile-time coverage for struct layout, field offsets, and enum values is often already present.
- **"Posted" usually means "written into my PENDING review," not "submitted to GitHub" — verify before treating a finding as live.** A finding you're certain went out in an earlier round can be absent from all three places at once: not in the pending review's comments, not an issue comment, not a comment on any submitted review. Check `reviews/<id>/comments` (pending) *and* `pulls/<n>/comments` (submitted) filtered to your login before carrying a finding forward as "already raised" — otherwise it silently never reaches the author.
- **A finding with no file/line anchor cannot ride in the inline set and will vanish at submit.** Commit-message-level asks (a missing `DEPENDS_ON:` line, a stale PR title/body, a ticket-key mismatch) have nowhere to attach. They must go in the review body or as a standalone issue comment. Keep an explicit "anchorless" bucket in the draft and reconcile it against the submitted comment list afterwards — a review can come back 26/27 complete with the one structural blocker missing.
- **A line shown as *removed* by a PR may actually have been *added to `main`* after the branch point — verify before drafting any "why did you delete X" finding.** When the branch is behind `main`, GitHub diffs branch-vs-current-main-tip and paints lines that `main` gained (via an unrelated commit the branch doesn't have) as red deletions, even though the PR only adds. Two-step confirm: `git show <merge-base>:<file> | grep '<line>'` (absent at the merge-base = the branch never had it) and `git log -S'<line>' <merge-base>..origin/main -- <file>` (finds the separate main commit that introduced it). If that commit isn't in the branch, it's a rebase-lag artifact — the fix is "rebase," not a real deletion. The tell: a purely-additive local `merge-base..HEAD` diff (+N/−0) that contradicts a red deletion in the GitHub view.

### Pick Battles & Scope
- **3 well-reasoned blockers beat 15 nits.** A representative outcome: 10 findings, 4 posted, 6 dropped/acknowledged. Only substantive issues should reach the PR — author energy is finite.
- **Distinguish PR-introduced from pre-existing issues.** When a PR refreshes one row of a doc table or touches one function, scope review to that change. Pre-existing errors elsewhere belong in their own PR; flagging them here dilutes signal.
- **Defer findings to the PR that introduced the code.** Issues uncovered while reading *moved* code (e.g. a `static const` in a header creating one copy per TU) belong on the introducing PR, not the move PR. The move preserves behavior; the introduction made the design choice. Note it for the right author and PR.
- **Don't push the same design concern twice.** If round-1 raised a design alternative and round-2 fixed the symptom without engaging the alternative, draft the re-raise to see what it would look like — then weigh whether it's worth spending reviewer credibility on. Often it isn't: the partial fix is defensible, the design works, and a second push reads as "didn't accept the answer." Waive explicitly in the audit row so the call is visible to future-you, not silent.
- **Socratic question > prescribed fix when the author may have hidden context.** When a value or design looks wrong but could plausibly be intentional (a tiny ring buffer, an ungated test helper, a magic constant), lead with a short question — "3 seems small, any realistic burst would overflow — perhaps I misunderstood the intent?" — rather than a multi-paragraph fix proposal. It invites the rationale, costs the author one line if intent is sound, and avoids re-litigation if you've missed something. Reserve prescribed fixes for cases where the defect is unambiguous.
- **HW-frozen / IP-owned tables don't drift — drop "future change breaks ARRAY_SIZE" arguments against them.** When a descriptor table is hardware-defined and owned by the IP team, the "someone adds a row and forgets to bump the size" angle is empty: it requires silicon, not a code edit. Style-only findings that survive only on hypothetical future churn aren't worth posting.
- **Before carrying a "why not make this narrower/simpler" finding into round N+1, confirm the value isn't mechanically forced by the IP.** Parameters that look over-wide or redundant (a selector that includes always-zero bits, a table whose upper entries just mirror the lower ones) are often not free choices at all — the hardware derives them by a fixed rule, so the "waste" is unavoidable and the code comment already says so. One check against the IP knowledge base retires the finding outright. Mark it **stale/dropped** in the audit table with the mechanism named, so future-you doesn't re-raise it a third round.
- **Drop the finding when you don't actually care.** If a scope-creep / ticket-hygiene / process-only call doesn't materially change the review outcome and you'd post it only "for completeness," drop it. The verdict and substantive blockers are the signal; weak ride-along comments dilute them.
- **A hierarchical-path logger that drops all but the leaf loses locate-ability — that's a real finding, not a droppable nit.** When an interrupt/cause-tree (or any `root/aggregator/leaf` walker) logs only the terminal node — because the intermediate hops take the silent "descend" branch — the operator sees `leaf` with no idea *which* instance/aggregator it came from, and can't map it back to the firing source. Don't wave this off as diagnostic-only cosmetics (I did once and a co-reviewer rightly raised it): a per-hop `LOG_ERR("%s/%s", node, bit)` at the descent restores the full path across log lines at near-zero cost. Weigh "can the operator find the interrupt from this line alone?" before dropping a logging-coverage finding.

### Working With the Author and Other Reviewers
- **A branch-split restructure orphans pending drafts and needs the review task repointed.** When an author closes a whole multi-PR set and reopens the work across new branches (and/or adds repos), map old→new, repoint the task's PR entries to the live numbers, and recreate any pending inline drafts on the live PR — a pending review left on a closed PR is stranded. First check the live PR: the author may have already addressed your orphaned comment (mooting it).
- **Verdict mechanics: attach a request-changes verdict to already-drafted comments by *submitting the existing PENDING review* (event REQUEST_CHANGES, empty body), not by creating a new review.** An empty-body REQUEST_CHANGES with no inline comments is rejected by the API, so a PR carrying only an already-submitted standalone COMMENTED review can't be flipped to request-changes without a body — surface that constraint rather than inventing body text. APPROVE accepts an empty body.
- **Tone-calibrate for junior / AI-assisted authors.** Be direct, casual, name the failure mode in user terms ("you only find out from an ELBI timeout at runtime"), avoid jargon ("idempotency"), don't stack multiple equivalent options when one is clearly right. "This will bite us" / "Don't leave dead lists in the code" lands; a multi-paragraph design essay doesn't. The bar is *what does a junior reading this actually do next?*
- **When accepting a phasing/TODO decision, require it be promoted to `/* [TICKET-ID] TODO: ... */` form, not just left as a bare comment.** Bare TODOs rot silently and are invisible to grep across the ticket tracker. Asking the author to open a JIRA and reference it in the code comment turns the deferral into a tracked, discoverable obligation — at near-zero cost to the author. Apply uniformly whenever you waive a finding on phasing grounds.
- **Read the author's own pending draft thread first.** Before drafting, fetch the author's pending review comments (GraphQL `pullRequest.reviews(states: PENDING)` returns the user's own drafts). High chance some findings are already drafted in their words — focus on the gaps.
- **The user may already have a PENDING review with draft inline comments — query for it explicitly.** A bare `reviews`/`comments` fetch returns *submitted* state only and comes back empty, masking your own drafts; you'll "discover" a clean slate and double-draft what's already written. Always run `reviews(states: PENDING) { comments { path line body } }` for the viewer up front and fold those into Findings before adding new ones. When the user says "consolidate my comments," they mean these.
- **Posted comments own the knowledge — never cite RTL signal names, source file paths, or "verified against" framing in the public text.** Internal evidence (e.g. `allow_log_*` / `csr_axi_termination_pkg` / "Log only 1st error" RTL quotes) belongs in the draft notes and per-IP knowledge base, never in the inline. The posted comment states the observation and the fix in the reviewer's voice — "this never clears the sticky STATUS bits, so the capture freezes after the first event" — not "I read `el_axi_terminator.v` and `allow_log_wr` is gated on `~status_aw_term_occured_data_r`." The author shouldn't have to follow the reviewer's research trail; they should see one durable, FW-actionable statement.
- **Internal classification tags (`[QUESTION]`/`[SUGGESTION]`/`[BUG]`/`[POLISH]`) are draft-only triage markers — strip before posting.** They exist to help the reviewer sort the draft and shape the final verdict; on the PR they read as either bureaucratic or condescending. Posted text starts with the substance, not the label.
- **Read other reviewers' posted comments and threads before drafting.** Avoid duplicating signal; build on or defer to existing threads.
- **A new `--approve` overrides your own earlier `CHANGES_REQUESTED` — no separate dismiss needed.** When a prior round left your `CHANGES_REQUESTED` and the concern is now addressed, submitting a fresh approve flips the PR off your block (decision moves from `CHANGES_REQUESTED` toward `REVIEW_REQUIRED`/`APPROVED`); you don't have to hunt down and dismiss the stale review. Confirm the code actually resolved it first (e.g. a `.gitignore`-only fix for "don't commit X" is complete only if `git ls-files` shows X is no longer tracked — the ignore rule doesn't untrack).
- **"For now we approve; author fixes in a future patch" → park the comments, don't post them.** When the user accepts a landing with agreed follow-ups, record the deferred items in the draft (and task notes) as parked/future-patch, keep the verdict `approve`, and don't open threads on the current PRs. The parked list becomes the seed for the follow-up patch's review, not noise on a PR everyone already agreed to merge.
- **Let the author post their own comments where it fits.** For some findings, the author phrasing them in their own words gives better ownership and tone.
- **Author redirect dropping a finding is a green flag, not a loss.** "I've already drafted that" or "I disagree, here's why" — if the reasoning holds, drop the planned comment without re-litigating. Signal-to-noise of the posted review matters more than coverage.
- **An author's reply can open with the exact reasoning you already rejected yet still have fixed it correctly — read the whole reply and the code, not the opening clause.** A reply that leads "init runs single-threaded, no preemption to guard" (the round-1 justification you pushed back on) can go on to describe a proper fix (a busy-reject gate that covers the preemptive path). Don't treat a partial-sounding opener as pushback; verify the full reply against the current code before re-raising a settled finding.
- **The author's own fix can beat your prescription — leave room for it.** When posting "consider X," the author may find a cleaner Y you missed (an existing public API you didn't grep for, a named macro you didn't know about, an integration point already established). This reinforces the Socratic-question pattern: state the concern, sketch one path, but don't insist on the exact mechanism. Accept Y when it solves the underlying issue more cleanly than X would have.
- **"Author tested it" can close a correctness pushback.** When the concern was correctness (not style) and the author runs the code and confirms behavior, that's a valid resolution even without a code change. Reserve insistence for shape/readability issues where testing doesn't address the concern.
- **Cross-link identical constants across sibling PRs rather than re-litigate.** When the same magic number (timeout, register value, retry count) appears in two PRs from the same author, post the substantive comment on one and a one-line cross-link on the other. One Kconfig hoist resolves both; review doesn't fragment.
- **Strip dialogue-born endorsements from the posted comment.** When the reviewer↔user walkthrough concludes "good call / the author's approach is right," that praise is an artifact of *this* conversation, not signal for the author. The posted text leads with the substance ("nothing places this section, so the DMA path has no anchor — add the fragment"), not a "good call, but…" preamble that only makes sense if you saw the discussion. Same family as stripping `[QUESTION]`/`[SUGGESTION]` tags: the PR sees the actionable statement, not the triage trail.
- **Write for a non-native English reader by default.** Short sentences, plain vocabulary, no rhetorical flourishes or multi-clause build-ups. Where you'd describe the shape of a fix in prose, scaffold the actual code instead (the enum, the four `#define`s) — a concrete snippet crosses the language gap that a paragraph doesn't.
- **Split a long analytical finding by *anchor location*, not by paragraph.** One comment per code site. A four-paragraph comment spanning three files gets read once and acted on partially; the same content as three anchored comments each gets its own thread and its own fix. Do the split at draft time — decide which line each half belongs on before writing either half.
- **Re-read a trimmed comment standalone before posting it.** Cutting a finding down to "just the last paragraph" routinely leaves a dangling back-reference ("If you prefer to defer the split…") pointing at text you removed. Trims need rewriting, not just deleting.
- **Fact-check the *reviewer's own* draft text as hard as the author's code.** When the user rewrites a finding in their own words, verify every HW/spec claim in it before endorsing — a reset-domain claim naming one reset type too many, or a "these table names don't match" assertion that turns out to be exactly right, will otherwise ship as reviewer error. Being wrong in a posted comment costs more credibility than the finding was worth.
- **Author/maintainer design intent can flip a finding mid-walkthrough — reverse cleanly, don't half-hedge.** A finding can invert when the user supplies intent you couldn't see from the diff (e.g. "that section is deliberate — it's how a debug DMA sources alternate FW"). When it does, don't keep the original framing with a hedge bolted on; re-derive from the new premise and rewrite the finding (here: "drop the section, `.rodata` is what we want" → "keep the section, but wire it to a fixed location with boundary symbols"). Move the abandoned version to Dropped with the reason so the reversal is visible, not silent.

### Re-Review After Force-Push / Rebase
- **Diff the prior reviewed SHA against the new head and triage per file.** Comment-addressing fixes get scrutinized; unrelated rebase artifacts (path repaths from sibling-repo splits, CI config additions) get a glance and a pass. Don't re-review files that didn't change since the last pass.
- **A re-pull that fails with "Not possible to fast-forward" — with the local branch both ahead *and* behind — means the author force-pushed/rebased, not a merge conflict.** For a clean review checkout with no local work of your own, the stale "ahead" commits are the pre-rebase tips; confirm the working tree is clean, then align to the new remote tip with `git reset --hard origin/<branch>` rather than merging (which would fabricate a merge of superseded commits). A *missing remote ref* on the same fetch (`couldn't find remote ref …`) usually means that repo's PR merged and its branch was deleted — switch that repo to `main` instead. Re-verify all draft findings against the new tips afterward; a rebase invalidates earlier diff snapshots.
- **Resolve the *prior-pass* head, never the head you just recomputed this session.** A rebase changes the head SHA even when your freshly-derived head already equals the PR head — so head-equality proves nothing. Pull the baseline from the prior draft's `Head SHA reviewed`, the task notes' `reviewed @ <sha>`, or GitHub's `reviews.commit.oid`. Fetch the orphaned old SHA by hash (`git fetch origin <sha>`) — rebases don't delete it. Then confirm "no new code" only via `git diff --name-status <old>..<new>`; never conclude "nothing changed" from matching heads. New files (a driver split, a new backend `.c`) are exactly what hides behind a SHA-equality shortcut.
- **A remote force-push can GC the prior head's branch ref so `git fetch origin <sha>` fails — but the object usually survives locally.** After a `pull --rebase`/force-update, the old head lives in the remote-tracking reflog (`git reflog show refs/remotes/origin/<branch>`) and its object is still in the local store (`git cat-file -t <sha>` → `commit`). Recover the baseline from there before concluding it's unrecoverable; only then fall back to the prior draft's recorded SHA.
- **On a squashed/rebased single-commit re-review, the commit subject describes the whole squash-vs-main, not the round-over-round delta.** A subject like "take die offset; drop X" reads as fresh work when the touched code files are byte-identical to the prior-reviewed head and only one unrelated file actually changed. Blob-hash each touched file across `<prior-sha>:<file>` vs `<new-head>:<file>` (`git rev-parse <sha>:<file>`) — IDENTICAL hashes mean skip the re-read. Trust the hashes, not the squashed subject line.
- **Removing a feature can moot an entire dependency stack — re-check `DEPENDS_ON` every round.** When an author deletes a mechanism (rather than plumbing it), the multi-PR stack that supported it (infra accessor + slot-allocation PRs) can vanish from the deps, making the PR self-contained. A dependency that was real last round can go stale; conversely, verify each *surviving* leg is still needed and not stale-by-mis-association (a same-branch sibling PR in another repo may cover an unrelated feature).
- **Record the reviewed head SHA(s) at review-done.** Multi-repo sets need one per repo. The next pass diffs `that-sha..new-head` instantly instead of re-deriving the baseline (and risking the equality trap above).
- **Don't assume a rebase is clean.** Commit content dates can stay the same while committer dates change. Check for silent changes and for JIRA ticket renumbering in commit messages — renumbering can signal scope changes.
- **Re-confirm `headRefOid` mid-pass; force-pushes happen during the review window.** Pulling thread state and pulling the diff can straddle a force-push, leaving you reviewing an old head with a fresh thread list (or vice versa). After fetching threads and before drafting, re-query the PR's `headRefOid` and re-fetch if it has moved since your local checkout. A second force-push within the same session is not rare.
- **Amended-commit re-reviews are fast.** `git diff <old-sha>..<new-sha>` gives exactly the incremental change; no need to re-read the whole PR.
- **Verify replaced cross-repo dependencies independently.** When an author swaps a dependency PR in another repo (e.g. infra PR closed, replaced by proj_infra PR), re-verify the new dependency — it may be trivial (a DTS alias) or introduce subtle changes.
- **Don't flag a symbol/include as "dead" from a workspace sitting on `main` while its defining branch is unmerged.** A "route it through infra" fix commonly fans into a multi-PR stack (feature repo + a `module.infra` accessor + a `proj_infra` slot/alloc header). If the constant an include provides (e.g. a cold-flop slot) lives in an *unmerged, unchecked-out* dependency branch, a local grep on `main` finds nothing and the include looks dead — a false positive. Before drafting a dead-include/unused-symbol nit, fetch/checkout every leg of the stack (read `DEPENDS_ON:` in the commit body and `gh pr list --head <branch>` across the sibling repos) and confirm the symbol truly has no definition anywhere in the stack. A review-mgr task that gains a PR *after* `start` won't have that repo checked out either — its branch must be checked out (not just fetched) before any "it's not on disk / not referenced" conclusion.
- **Per-file content-diff bypasses rebase-pulled main commits.** When a rebase drags unrelated main commits into the range, raw stats and unified diffs balloon and obscure the author's delta. Compare `<(git show old:file) <(git show new:file)` per file the author touched — isolates true author changes from rebase noise.
- **On a re-review, `gh pr diff` is the authoritative scope filter — not the `old-reviewed-SHA..HEAD` window, and not `git branch --contains main`.** When a branch is rebased onto an *unmerged stacked base* (a dependency branch, not main), the re-review window pulls in the base's commits — often under *different ticket keys* — which masquerade as this PR's scope creep. The `is-it-on-origin/main?` test is misleading here: those base commits answer "NOT on main," so they look branch-only/in-scope when they're actually below the PR base. Confirm true scope two ways: `gh pr diff <N> --name-only` (files that aren't in it aren't the PR's) and `gh pr view <N> --json baseRefOid` (if the base SHA *is* the unrelated commit, everything under it is out of scope). Drop the base's files from the review; note that the PR can't merge until its stacked base lands (`gh` flags it CONFLICTING).
- **Combine the scope filter with a per-file blob compare to get the author's true round-over-round delta.** On a branch rebased onto an advancing stacked base, `prior-head..new-head` is mostly base noise — it can show dozens of unrelated files and hundreds of added lines in files the PR barely touches, which reads as scope creep or a suspicious new subsystem. Two-step recipe: take the file set from `gh pr diff --name-only` (that *is* the PR), then for each of those files compare `git rev-parse <prior-head>:<file>` against `<new-head>:<file>`. Identical hashes = untouched since the last pass, skip it. This simultaneously proves which files really changed and dissolves "why is this huge unrelated file in the diff" — the growth belongs to the base. Report the scope correction explicitly so the author isn't defending churn they didn't write.
- **When a PR reverts its own change and then un-reverts it, verify the named root cause in code — and check the ordering of the fix against its consumer.** A three-commit "do X / revert X because Y broke / redo X, Y is fixed now" sequence hands you a specific, falsifiable claim. Open the commit that allegedly fixes Y and confirm it does. Then look for the ordering trap: the fix usually depends on some state being set before the step that consumes it, and the un-revert commit is exactly where that invariant is easiest to get wrong. Trace whether the setter runs before the consumer — if the consumer is a "select"/"configure" call that only records state, and the real programming happens later from another thread, the ordering is fine; if it programs immediately, the bug is back. Checking this and finding it clean is worth saying out loud in the review: it's the difference between "approved" and "approved, and here's why I believe the revert reason is really gone."
- **Build a prior-comments resolution audit table before drafting new findings.** One row per prior thread, marked resolved / accepted / partial / waived. Forces explicit triage of round-N+1 against round-N, surfaces selectively-addressed concerns, and makes the verdict justification write itself. Partial ≠ ignored — the named symptom may have been fixed even when the proposed alternative wasn't engaged with.
- **Carry prior waiver decisions forward; don't re-promote a waived finding on re-review.** A finding that reviewer-and-user jointly waived as near-zero / not-worth-posting on the first pass stays waived unless the new diff *changes the underlying analysis*. A pure rename (or any behavior-preserving refactor) of the code the finding touched does not reopen it. Before escalating a parked item to a blocker in round N+1, confirm the code path's semantics actually changed — otherwise you're re-litigating a settled call and will have to walk it back.

### Code-Move & Multi-Repo Refactors
- **A move that relocates HW programming out of a driver that owns a reset-restore callback into a one-shot device init silently drops reset-survival.** When code that programs a register block is moved from driver A (which re-runs its init on every soft/hard/warm reset via a reset-manager callback) into driver B's one-shot `*_init` (device init runs once at cold boot, no reset hook), the block reverts to reset values after any such reset and nothing re-programs it — a latent functional regression no cold-boot test catches. The tell: driver A still re-programs a *sibling* block in the *same* register file on every reset (proof the block loses state), while the moved code now has no reset caller. Grep the destination driver for `el_reset_register_callback`/reset-callback registration; if absent and the source had one, the reset-restore path was left behind. Fix: either the new owner registers its own reset callback that re-invokes the programming on POST, or the source driver calls a single facade from its (reset-restored) init. "It's a temporary home, moving later" does **not** excuse breaking reset in the interim — the reset hook must move *with* the logic, or it gets unwound twice.
- **Hash-compare moved blobs, don't eyeball them.** `sha256` of each blob — pre-move source vs post-move destination — collapses correctness to "did the bytes change in transit?". Read moved files only if hashes diverge or the move is paired with intentional edits.
- **Compare against the cleanup commit's parent, not the source repo's main tip.** Use `<deletion-commit>^` in the source repo; comparing against source `main` HEAD returns empty-file hashes because the files are already gone there.
- **Verify the deletion set equals the addition set.** For large deletion PRs (tens of thousands of lines), line-by-line review is meaningless. Cross-check: `diff <(git diff --stat | sort) <(git -C ../other diff --stat | sort)`.
- **Build-system repath changes are the high-signal part.** File moves are mechanical; the cmake/Makefile/starfile/`module.yaml` changes that update include paths are where bugs hide. A wrong root prefix (`ip/infra/` vs `infra/`) silently compiles against the old location while the old branch still has the files. Verify root variables (`MODULE_INFRA_ROOT`/`INFRA_ROOT`) match what consumers reference.
- **Consumer PRs prove the split.** In a multi-repo split, source and destination define the split; the consumer PRs (tools, proj_infra, fla_rom) prove it works by updating every include path. Review them carefully even when they look trivial — any missed path is a build failure.
- **Filter three recurring false-positives when validating "unreferenced" deletion claims:** (a) peer files in the same script bundle referencing each other, (b) build-artifact snapshots that re-publish and self-reference the tree, (c) commented-out cmake/build blocks.
- **Before worrying that a deletion breaks a *claimed* consumer path, confirm that path is actually live.** A `zephyr_library_sources_ifdef(CONFIG_X ...)` (or any `ifdef`-gated reference) whose `CONFIG_X` has *no `config` definition anywhere* is dead — the guard is permanently false, so the listed sources are never compiled. Combined with the guarded files being neither tracked nor present on the base (introduced only by a sibling unmerged PR), the "does deleting the artifact break the builtin path" question dissolves. Three-part check on any deletion PR: (a) does the gating Kconfig symbol even have a `config` block, (b) do the guarded sources exist on the base branch, (c) who actually reads the deleted file *as a build input* (grep the base, excluding docs and size-macro references). Only a live path that reads the deleted file is a real break.
- **Anchor or word-boundary substring greps.** Bare substrings generate noise (`expect_sc` matches `expect_scan`; `dirty_check` matches commented build lines). Use word-boundary regex or eyeball each hit's context before reacting.
- **Rename PRs: grep the old name in *comments*, not just code, and exclude build artifacts.** A rename that compiles and ships can still leave a stale `/* uses old_name */` in an adjacent file the PR didn't touch — invisible to the build, misleading to the next reader who greps. Workspace-wide hit lists are dominated by `build/`-tree codegen (devicetree_generated.h, .obj, edt.pickle, zephyr.dts) which masquerades as "dozens of consumers" but is just stale build state; filter `build/` out before counting. Real surviving consumers — and stale comments — surface cleanly only after that filter.
- **A public-symbol rename is only complete once you've grepped the repos the PR set *doesn't* contain — and "CI is green" does not clear it.** When a rename deletes the old name outright (no compat `#define`), the dangling consumer is typically a DTS/overlay or config in a sibling repo that isn't one of the PRs. Two filters make the grep usable: exclude `build*`/`build_artifacts/` **and** any local mirror/sync tree (`.rsync_data/`-style), which together produce hundreds of stale generated-DTS hits that drown the one real match. Then apply the decisive check: a board overlay existing on disk does **not** mean it is built — open the app's starfile board list and confirm whether that board is actually in it. A rename that breaks only unbuilt boards passes CI and detonates for whoever enables one, with an opaque preprocessor/dtc error and no breadcrumb. Ask for the one-line sibling-repo PR (or a compat alias) so the rename lands complete.
- **DT `reg-names` rename: the binding yaml that doesn't enumerate `reg-names` accepts any list, so no schema update is required — but consumer breakage is silent at build time.** Verify completeness by grepping every `DT_INST_REG_ADDR_BY_NAME[_OR](*, old_name…)` against the changed compatible across the workspace. By-name lookups don't link-error when a name disappears; they just resolve to the wrong block or zero (with `_OR`). Treat this as a "second consumer" check tied to the compatible string, not the file.
- **Board overlays belong in the application directory.** Zephyr convention is `<app>/boards/<board>.conf` + `<board>.overlay`. A `projects/<product>/<app>/boards/` indirection adds cmake complexity (`BOARD_OVERLAY_SEARCH_DIRS`, product-selection vars) for no gain — the build already searches `<app>/boards/`.
- **Eliminate single-valued indirection variables early.** A `TOOLS_PROJECT`/product cmake variable that defaults to the only valid value and threads through starfiles, cmake, and paths is complexity debt. Add multi-product plumbing when the second product actually arrives.
- **`add_subdirectory_ifdef` ordering is rarely a review point.** Driver-list ordering in cmake is seldom strictly alphabetical; don't flag it unless the file enforces it.
- **On a fail-loud build-config migration, audit every entry point for consistency — the one path that falls back to a default/`nil` is the real finding.** When a change makes the build refuse to guess (missing selection → hard error) across cmake (`FATAL_ERROR`), Makefiles (`$(error)`), shell wrappers (`exit 1`), and lua (`error(...)`), the design's value is the *uniformity*. Grep every consumer that assembles the moved roots and confirm none silently degrades — e.g. a lua base-dir set via `PATHS[1]` from an unchecked glob concatenates `nil` (opaque runtime error) instead of the clean message its siblings emit. That single inconsistent path is the only thing worth a comment on an otherwise-clean fan-out; everything else is mechanical.
- **A helper that newly reads a required struct/dict key unconditionally = run the second-consumer/KeyError grep.** When a shared path-builder starts dereferencing a field that only exists after an enrichment step (`board["_csr_project"]`, an "expanded" entry), grep *every* caller across the workspace and confirm each passes the enriched form — a single caller passing the raw struct is a hard failure that no local build surfaces if that repo's config isn't the one exercised. Same family as the compile-coverage check: the break hides in the un-exercised caller.
- **Multi-repo board/config fan-outs are dominated by one mechanical edit — verify uniformity, then spend attention on the few resolver/consumer files.** A 25-repo "add `project=` to every board / repath the includes" set is ~90% a single find-replace; diff one representative against the rest to confirm they're identical, and concentrate the real review on the handful of files that assemble the `-I` roots and the code-gen scripts (where a wrong prefix silently compiles against the old tree). Don't line-by-line the mechanical repaths.

### Abstraction & the "Second Consumer" Test
- **Grep for the second consumer before approving any "vendor-agnostic / pluggable / drop-in" API.** If it doesn't exist, the API shape is speculation — push to land only what has a real caller today.
- **A "safe accessor" infra PR that fixes a blind-cast Bug fixes nothing until the consumers migrate — the offending assumption lives in the consumer casts, not the shared header.** When a Bug's root cause is a blind `(sub_api_t *)dev->api` cast (an offset-0 assumption), adding a typed accessor macro/helper to the shared header removes *zero* offset-0 assumptions: they physically sit in each consumer's cast and each producer's struct layout, none of which a header-only PR touches. Verify where the assumption actually resides before crediting a "fix" — a change to a shared type can't fix a bug embodied in code it doesn't edit. For a Bug ticket, insist the consumer migration (and a producer that adopts the new shape) land in the *same* PR, or the bug ships byte-for-byte unchanged behind a doc that now merely *claims* it's fixed. Landing the mechanism alone also leaves the broken pattern as the only worked example in the tree, so the next author copies it and reintroduces the bug.
- **On the follow-up consumer-migration set, grep the whole subsystem for the blind-cast pattern and confirm the consumer set is *complete*, not just representative.** A migration that converts N-1 of N consumers reads as done at a glance; the missed one is typically the consumer whose *producer driver lives in a repo not in the set* (so it genuinely can't be finished there). Distinguish "can't finish here → defer + track (sync with that repo's owner)" from "forgot" — and note that the surviving caster is exactly what still justifies the transitional `offsetof==0` BUILD_ASSERTs *and* is the worked example the next author copies. The transitional asserts + "drop once every consumer uses the accessor" comment are the correct bridge while one consumer remains deferred; don't call them stale until the last consumer lands.
- **Second-consumer test on helper inlines shipped alongside the migration:** if the migrated consumers hand-roll the exact body of a newly-added helper (e.g. the `if (api && api->op) api->op(...)` NULL/`-ENOTSUP` dance) instead of calling it, the helper has zero consumers — route the consumers through it (centralizes the contract) or drop it until there's a caller.
- **The offset-0 sub-API blind cast collides the moment a device needs a second offset-0 sub-API.** Casting `dev->api` to a sub-interface type assumes those ops are the first struct members. A driver that must keep sub-API A at offset 0 (because *another* consumer blind-casts to A) physically cannot also present sub-API B there — B's cast silently resolves into A's table and calls A's ops with B's arguments (e.g. a `register_err_handler` that actually runs a rate-limiter `set_level`), corrupting state with no error. "Inert only because the DT node ships `disabled`" is a live latent bug, not a non-issue. Fix: a typed accessor returning `&drv_api->embedded_member` (compiler computes the real offset) — but only once consumers call it instead of casting.
- **A "must never do X" contract doc is self-contradictory while every teaching doc still shows X.** When a header's doxygen is rewritten to forbid a pattern but the developer-facing HOWTO/README/agent docs (often in a sibling repo the PR can't touch) still present X as the sanctioned recipe, the documented contract fights itself and a new author following the HOWTO reintroduces the bug. Grep the *docs* for the old pattern, not just the code, and require the teaching docs move in the same change as the contract.
- **A re-review that *promotes* a plain internal helper into a full public `__syscall` + vtable op is fresh API surface — re-run the second-consumer test even mid-feature.** When an author restructures `void internal_fn(...)` into `_impl` + a guarded `__syscall`/`z_impl` + a vtable entry (often to match a just-landed ownership/permission model), the init path frequently keeps calling `_impl` **directly**, leaving the syscall/vtable op with zero callers. The tell: the sibling config ops follow the identical op-exposure pattern *but each has a live consumer* (a shell command, a manager path) while the new one has none — that asymmetry, not the pattern itself, is the signal. Non-gating question ("runtime-reconfig consumer coming, or keep it internal until there's a caller?"), not a blocker; the restructure is defensible as forward-looking infra.
- **Identify independent variation axes before approving a single vtable.** Two reuse axes (e.g. swap vendor vs swap integration glue) need two composing device classes, each with its own DT node and driver, linked by phandle — not one vtable inside the vendor driver. Mixing axes defeats the stated reuse: the vendor driver carries integration code, and integration paths share nothing.
- **Renaming leaf calls is not abstraction.** If both consumers still own the same multi-step sequence (enable → load → unhalt → poll) and only per-step names changed, the reuse is cosmetic. Promote the *orchestration* into an op so consumers share the call, not just the leaf names.
- **A "future-proofing" enum value or branch with no consumer is dead code in disguise.** Push to drop it; let the consumer-introducing PR shape it correctly.
- **Offset-as-parameter leaks driver arithmetic into the API.** A `mem_addr_t die_offset` (or `stride * idx`) passed by every consumer forces caller-side stride math and bakes an unchecked "same stride for all bases" assumption. Prefer an opaque per-die id / handle / device instance so the driver owns the arithmetic. The "keep the vendor driver die-agnostic" argument doesn't require offset form — an index API where the driver multiplies by an integration-supplied stride (DT or Kconfig) preserves the same boundary while keeping callers clean.
- **Accept phasing, but each phase must stand on its own consumers.** "This is phase 1" doesn't excuse shipping dead branches or untested abstractions inside phase 1.
- **A wrapper/manager reaching directly for sub-block (IP) register names breaks layering even when it compiles via a generic accessor.** Approving the *register choice* isn't enough — also check *who* references it. When a higher-layer driver names a vendor/sub-block register (e.g. `AW_*` regs) instead of going through that block's own API, flag it: register knowledge belongs in the owning driver, exposed as a typed call. Don't let a correct register hide a layering violation.
- **A newly-added `<*_regs.h>` include is the cheapest layering tripwire in a diff — scan the include block first.** If a file that previously had no register-header dependency grows one, the code manipulating those registers is usually in the wrong layer; the include is the visible symptom of an invisible boundary crossing. Two outcomes are legitimate: the code moves down into the block's own driver, or the file genuinely owns that block (e.g. an EP-only wrapper belongs in the EP driver, not the shared vendor PHY driver). **The non-negotiable part is that the register class ends up with exactly one owner** — when the same block is already poked from another file, the finding isn't "which file is right" but "pick one and consolidate." Frame it that way and let the author choose; arguing the wrong axis (which of two plausible homes) invites a debate that doesn't change the defect.
- **A brand-new header carrying one small primitive is almost always a naming problem, not a placement problem.** The tell is a domain-qualified name on a domain-agnostic operation — `el_piw_ecc_cause_read_clear(cause_reg, clear)` is just read + write-1-clear; nothing about it is ECC. Ask two questions in order: (a) is the operation actually specific to the domain in its name, and (b) does an existing common header for that subsystem already hold the accessors it's built on? When the answer is no/yes, rename it generically and put it in the existing header rather than minting a new one. Header count is real cost — every new file is another include-order decision and another thing to grep. Note that the "dependency-free / no CONFIG_X coupling" rationale for a separate header usually evaporates once the helper is generic: the common header it belongs in is typically already dependency-free for the same reason.
- **A "compatibility wrapper" needs a named external consumer.** If a migration turns the old symbol into a one-line forward and grep shows zero in-repo callers, ask which downstream repo needs the old name. If none, it's dead code with a flattering label — delete or document the consumer.
- **Superseding PRs: verify the overlap explicitly.** Diff commit messages and content; don't take the author's word that a new PR fully covers the old one.
- **Before a deep review, check whether an in-flight PR supersedes this one — including your own.** A small targeted feature PR can be made moot by a larger refactor/centralization PR landing in the same repo. Scan the task/feature tracker (task-manager, pr-monitor) and open PRs touching the same file for a competing change before sinking time into a line-by-line pass. The tell: an existing reviewer comment saying "this belongs in <component X>" where X is an actual in-progress effort. When two PRs edit the *same lines of the same function* in opposite directions (one deletes the mechanism, the other extends it), they are mutually exclusive — they cannot both merge, so the review reduces to "which one wins" and a pointer to the survivor, not a nit-by-nit critique. Confirm the collision by diffing both branches' versions of the file against their shared merge-base, then recommend closing the superseded one and name the PR that carries the ticket.

### Hardware / Register Correctness
- **Resolve *which* register map the build actually consumes before claiming a symbol doesn't exist.** A stale or wrong-project copy under `~/build_artifacts/` can expose the same block through a materially different interface than the workspace's own generated specs (e.g. an indexed `RD`/`WR_ADDR` viewport in one revision vs a `POP`/`EMPTY`/`ENTRIES_CNT` FIFO with split `ENTRY_DATA_0/1` at different offsets in another). Finding the driver's symbols "missing" is almost never a real defect — CI would not have compiled it — so treat the absence as evidence your map is the wrong one and go find the one the workspace builds against. Worth converting the surprise into a forward-compat note instead: if the next silicon revision reshapes the access path, a driver built on the current shape won't port, which matters to any middleware layered on top.
- **Field-width correctness says nothing about field *meaning* — trace the write-enable, not just the mask.** A driver can extract every bit correctly (right offsets, right widths, right 64-bit split across two mask registers) and still be semantically wrong about what the register *does*. The classic trap is a "state mask"/"filter" register that never gates the capture write at all: in RTL the FIFO write-enable keys off the raw event, while the mask feeds a *separate counter*, and that counter against a threshold is what **stops** capture. Qualifiers compound the inversion — the match may require *both* endpoints of a transition to be in the mask (it qualifies edges, not states), and the counter may be *cleared on every non-matching event* (so it counts *consecutive* matches, making the pair a thrash/flap trigger rather than a cumulative filter). A consumer that trusts a "set = capture" comment then gets the exact opposite behaviour: a full unfiltered log that silently halts early. Read the `assign`s for the write-enable and the counter set/inc terms before accepting any "filter" naming — and when the misunderstanding likely originated upstream, say so: the *spec* command definition probably needs the same correction, not just the driver.
- **A comment claiming a value is "already packed per ENCODE()" while the code still shifts it is self-contradictory — verify the packing against real data before flagging a "double-shift bug."** A coordinate macro that does `(rtr_yx << ENCODE_X_SHIFT) | (mod & MASK)` under a comment "rtr_yx is already Y:X packed per EL_NOC_ENCODE()" reads as an obvious double-shift defect (it fooled an automated pass into a false bug report). But the source `rtr_yx` (from a fiu-oam-table DT prop, `0x18`/`0x19`) is packed in the *producing block's* format (X at bits[3:0]), two bits below the NoC encoding — the shift is exactly what lands Y:X in ENCODE position before OR-ing mod_id. Prove it by evaluating the macro against the *consumer's own default map*: `CDUP_COORD(0x18..0x19, i)` → `0x60..0x66`, byte-matching el_noc's `CDUP_COORD_BASE..MAX` (= `EL_NOC_ENCODE(1,8/9,i)`). Code correct, comment wrong: the real finding is the misleading prose (a maintainer could "fix" the working shift). Decode the constants, don't trust the comment's claim about the format.
- **When a Capability register and its Status counterpart encode the same attribute differently, don't assume a sibling attribute shares one encoding for both.** If a PR splits *width* into two enums (CAP 0-based vs STATUS 1-based per the MMR spec) but keeps *speed* as a single enum used for both the CAP write and the STATUS decode, that asymmetry is the tell — the STATUS decode may be off by one notch (top value hits an "unknown"/fallback). A reference/SV decoder using the same table corroborates self-consistency but does not prove correctness (it may share the assumption); verify the STATUS field's offset in the spec. Diagnostic-only path → question, not blocker.
- **A word-sized `memcpy` read from a normal-memory buffer is correct on any target regardless of word-vs-byte codegen, and is the host-safe choice.** The "CPU must do 4-byte-aligned accesses" requirement is about the *register/MMIO* access path, not an in-RAM staging buffer or `.rodata` blob — byte reads of SRAM compose to the right word. `memcpy(&u32, p, 4)` avoids the UB of a `(uint32_t*)` cast (which UBSan flags on POSIX). Flag the *pre-existing* raw-cast siblings as the latent ones, not the new memcpy pattern; "author validated on the emulator" plus this reasoning closes the concern.
- **A cross-boot-stage "done" probe must read a *persistent* register, not a live interrupt-summary/status bit.** When FW checks whether an earlier stage (e.g. the ROM) completed a step, reading a live interrupt-summary roll-up that the runtime ISR reads-and-clears is unreliable — the bit can be serviced away before FW probes it, so the probe intermittently reports "not done" on a step that actually completed. Use a sticky software-scratch/spare field that no HW source drives and no ISR touches, repurposed as the stage-to-stage marker. When that marker is only a producer/consumer convention (not in the IP spec), it's acceptable *iff* the not-set path degrades to a safe documented fallback (e.g. a ROM-bypass boot sequence), not a hang/crash — verify that fallback and don't demand the producer (ROM) land in the same PR.
- **An enable/release-reset step needs a paired "is it running?" verify before the next step depends on it.** A bring-up step that ungates a processor (enable fetch, release reset) and immediately moves on assumes success; if the core never starts, the failure surfaces far downstream as a link/poll timeout with no pointer to the real cause. Ask for a status/heartbeat read after the enable, or at least a comment naming where the running-check happens. **The paired verify doesn't have to be a separate heartbeat read — an immediately-following dependent step that has its own timeout satisfies it**, as long as that step can only pass if the enabled block actually started (e.g. `enable_mcu` followed by a `wait_linkup` poll that returns `-ETIMEDOUT`: a MCU that never executes SRAM FW can't complete link training, so the timeout *is* the running-check). When the step sequence is commented so the downstream check is discoverable, accept the author's rationale and don't re-push for a redundant read — this is a settled, correct closure, not a partial fix.
- **A wrapper→IP-driver layering fix is verified by four checks, not just "the read moved."** When an author relocates IP-register access out of a wrapper into the owning IP driver to fix a layering violation, confirm: (a) the moved accessor uses the IP driver's own access idiom (same `el_die_indirect_read(cfg-><ip>_base + …)` shape as its neighbors), (b) the wrapper actually dropped the IP-register include (`aw_global_reg_regs.h`), (c) the new API is typed and self-documenting (`aw_d2d_read_sbinit_status()` returning the decoded status, not a raw reg value the caller must mask), and (d) any pre-existing generic accessor it replaced isn't left orphaned — grep it; it's fine if another consumer (an ISR) still uses it. All four green = clean fix, resolve the thread.
- **Multi-step HW init: verify the full step list against the production entry point, not the individual step files.** When a tool/script replicates an N-step bring-up sequence (PIW → iATU → BMU, or any analogous chain), open the file that *orchestrates* the steps in production (`el_pcie_ep_bar_map.c`-style) and diff the call list against the tool's. Missing steps can silently work for the test path and fail elsewhere — e.g. a contiguous BAR region accidentally matches a passthrough translation, while a scattered BAR silently routes to the wrong address with no error. Don't infer completeness from "the obvious init steps are there."
- **Two registers with the same field layout are still two definitions — flag a value built with the sibling's field macros.** When a driver writes one value to both `FOO_RESP` and `FOO_OTHER_RESP`, check whether it was *built* with `FOO_RESP__*_MSK/_SFT` and then reused. Identical offsets today make it numerically correct, so it isn't a bug — but the registers usually have different reset values (proof they're independent definitions), and the next spec regeneration that moves a field in one and not the other breaks it silently with no compile error. Cheap fix, real regen hazard; classify as a suggestion, not a blocker.
- **Pull the vendor manual before drafting a "why is this here" comment.** Invoke the relevant per-IP doc skill (EP-PHY vs SU/C2C, etc.) and read the register-field description first — it can flip the conclusion entirely ("why is SE doing this weird thing" → "SE is doing the right thing; the other side is latently broken").
- **Be ready to flip your finding mid-review.** Once the docs are in, re-derive the conclusion from scratch and post the correct framing, not the original hypothesis with a hedge.
- **Default/auto register paths are bring-up traps.** Vendor HW often exposes an "auto" trigger tied to a clock or reset edge (for power-gating exit). Using it during bring-up couples FW timing to something unrelated (e.g. `ref_clk_en`). Prefer the explicit-control override for first-bring-up; the auto path can stay for runtime PM.
- **Implicit timing dependencies on integration signals are latent bugs.** Code that "works today" only because an unrelated subsystem asserts a signal at the right moment is temporal coupling waiting to break. Flag it even without a failing test, and ask for the assumption to be documented in the wrapper header.
- **Diff what each instance writes when two driver instances share a vtable over the same HW.** Asymmetric register writes through a shared API — same in-arg, same physical PHY, different bits — are a contract violation: a latent bug on one side or an undocumented integration delta on the other. Surface before merge.
- **Two HW paths to the same effect → prefer the one already in the existing driver's footprint.** If a SW-control outcome can be reached via a wrapper-block register or a PHY-core register, and the PHY driver already writes neighboring bits in the core register on init, propose the core-register path: symmetric across wrappers, no per-integration replication.
- **One-way trapdoor bits deserve a dedicated comment.** A CSR that gates the very access path the host must use to clear it warrants explicit header-level documentation and ideally an asymmetric API split (`unsafe_enable` vs `safe_disable`). Verify in RTL where the gate physically sits — that determines which other CSRs go dark when set.
- **A production driver that deliberately omits a register-field write that a sibling/SV-test variant sets needs an inline note explaining the omission.** When the production path masks only the safe field (e.g. MSTR termination) and intentionally skips the fatal one (e.g. ELBI termination, which would lock out the clear path), the absence of the write looks like an oversight to the next reader. A one-line comment on the omission ("never set X here — it locks out the path needed to clear it") prevents a future "unify the two impls" change from reintroducing the fatal write. Don't ask to merge the variants if the test path legitimately needs the extra field.
- **Inline comment reads inverted → the comment is the bug.** When prose doesn't match the manual's field semantics, fix the comment. Readers trust prose over re-reading the manual; an inverted comment misleads long after the author is gone.
- **Distinguish edge-triggered from level-gated signals before reasoning about clearing/re-arming.** An "application" input the controller only samples as a level permit (e.g. a readiness/retry enable) is never cleared by HW and needs no re-arm — persistence across a block-surviving reset is harmless or even desirable. An edge-triggered action, by contrast, must see its gates open *at the edge*. Read the signal's I/O direction and "Registered: N/A" in the reference manual; don't assume "set bit → pulse → must clear".
- **Paired enter/exit reset handlers should bracket symmetrically — flag asymmetry as a question, not a blocker.** When one handler asserts a hold-off (CRS/retry) on entry behind a guard and its sibling releases it unconditionally on exit, surface the mismatch. It's usually benign (link is down mid-reset; the write is an idempotent RMW), so a question that asks intent — and proposes hoisting the assert above the guard for symmetry — is the right weight, not a blocker.
- **Compare timescales before flagging an event-gated notification as "dead code."** When an action fires on a physical edge (link DL_Up, training complete) but is gated by level enables set during FW init, weigh the FW config tail (µs of MMIO writes) against the physical event (ms of link training/equalization). If the enables are set long before the edge can occur, the notification fires correctly — it is not dead. Only the *recovery* path (event already past, no new edge) is the real gap, and there the notification simply doesn't apply. Re-derive when the author pushes back on timing grounds.
- **A write-only field documented as an explicit enumerated code list plus "for other values no change" makes every unlisted value a silent no-op.** Check each driver constant against the manual's `Values:` list, not against the constant's *name*. The classic trap is a `*_DISABLED 0x0` invented for symmetry when the encoding has no zero code — the disable function writes it, the hardware ignores it, the function returns success, and the block keeps running. Compounding tell: a name bound to the numerically-correct code for the *opposite* meaning (a "per event" constant holding the "all off" code), which detonates the first time someone reaches for the unused constant. Name such constants after the manual's value labels so the mapping is checkable by eye. The field being `W`-only ("read value is always 0") also means no readback will ever catch it.
- **Write-only registers need shadow state** for readback/debug; mask field values before writing; `BUILD_ASSERT` field widths against spec; zero/invalidate stale entries beyond a new table size on reconfigure.
- **Word-alignment of DT-derived sizes.** Passing a DT reg size to an API expecting a word count (`bytes / sizeof(uint32_t)`) silently truncates if the size isn't word-multiple. Prefer a `BUILD_ASSERT` at the binding/macro layer over a runtime check at the consumer.
- **Document the *why* of non-trivial HW magic constants** (tail_drop, credit count, enhanced mode). "Empirical knee", "HW capacity ceiling", "minimum to keep pipeline full" — a bare `CREDITS = 2` invites future tuning regressions.
- **A connected + enabled interrupt must never point at a no-op handler.** An `IRQ_CONNECT` to an empty stub plus `irq_enable()` on a level-triggered line is an interrupt storm waiting for the first assertion — the cause never clears, so the line re-fires forever. Stubs that exist only to satisfy `IRQ_CONNECT`'s non-NULL function-pointer requirement are the tell. Either the handler genuinely services (reads + clears the cause), or the line shouldn't be connected/enabled at all. Often latent because the config that activates the stub branch is mutually exclusive today with the one that declares the interrupt name.
- **A function-like macro used as a bare value (no following `(`) is NOT expanded — it becomes an undeclared identifier, a latent compile break.** When a helper macro takes an "operation"/"flag" parameter and callers pass a function-like macro name (`irq_enable`/`irq_disable`, which are `#define irq_enable(irq) …`) into a position that uses it *without* an argument list — e.g. as a ternary condition `param ? … : …` — the preprocessor leaves the token as-is, and the compiler sees a bare undeclared identifier. It compiles today only because the branch is guarded by a `COND_CODE_1(DT_INST_IRQ_HAS_NAME(inst, name), …, ())` that currently selects the empty arm (no board wires the named lines yet); the moment a DTS defines those `interrupt-names`, the true arm is emitted and the build breaks. The tell: a macro whose param name implies a bool (`en`) but whose call sites pass operation *names*, plus a sibling `if (enable){…}else{…}` that already branched on the real bool — two incompatible designs stitched together. Fix: have the macro call the passed op directly (`op(DT_INST_IRQ_BY_NAME(inst, name, irq))`) instead of re-deriving it via a ternary. Same family as "Green CI is not signal": the defect hides behind a DT gate that no built config exercises.
- **Separate "should this line be HW-routed" from "which handler services it" — they're orthogonal axes.** DTS `interrupt-names` (`DT_INST_IRQ_HAS_NAME`) answers the first; a Kconfig (e.g. tree vs direct) answers the second. Tangling them into one `#if/#else` produces dead branches (a HW-IRQ path stood up where servicing is actually by polling, or vice-versa). Factor a single connect helper parameterized on `(handler, ctx)` and pick that pair once per config; the per-line/per-config duplication collapses and each valid combination (shared dispatcher / direct driver ISR / poll-only-so-don't-connect) falls out cleanly. Confirm what the poll path (`el_irq_mon`-style) actually is first: a pure polling thread uses **no** `IRQ_CONNECT`/`irq_enable`, so "not HW-routed" means *connect nothing*, not *connect a stub*.
- **"HW works out of the box; enable just unmasks" closes the early-fire question.** When the only init step for an interrupt is `irq_enable()` (the cause/mask logic is HW-default-correct), connecting+enabling at an early init phase (PRE_KERNEL) is fine — there's no window where an edge hits an unconfigured handler. Confirm the masked-until-enable claim before dropping the timing question, but don't manufacture a deferral requirement the HW doesn't need.
- **A "configure" register group can be inert without a separate "arm/trigger" register — verify the enable that actually routes the datapath, not just the payload.** HW containment/drain-style blocks often split into a *payload* group (timeout counts, dummy response codes, a block-level `*_ENABLE` that only powers the response generator) and a *distinct* per-trigger arming register (e.g. an `ISOLATION_DROP.*_outbound_drop_en` field) that actually gates traffic into the block. FW that writes the whole payload + the block `ENABLE` but never the arming register configures cleanly and does **nothing** at runtime — no error, silently inert. Before believing "feature X is set up," trace in the IP doc / RTL (or the per-IP knowledge base) which CSR the activation signal is ANDed with, and confirm FW writes it. A block-level `ENABLE` is necessary-but-not-sufficient.
- **A finding rooted in *frozen* RTL (a HW tie-off the current silicon can't change) belongs in the per-IP knowledge base, not the FW PR.** When the deeper root cause is "the trigger is tied to `'0` in this RTL rev, so the feature can't fire regardless of FW," there is nothing the FW author can act on this tape-out — posting it adds noise and muddies the one actionable FW comment. Record it as a *verified next-silicon* item in the IP skill's knowledge base (instantiation chain + tie-off evidence) and route it to the RTL/spec owner out-of-band. Keep the PR comment scoped to what FW *can* change (e.g. the missing arming-register write). Confirm the RTL is actually frozen before deciding.
- **When auditing a producer/capture API, always check whether sticky status regs get cleared — compare to peer workers in the same diff.** AXI-terminator-style `STATUS` regs that gate their capture latches on `~*_OCCURED` (RTL: "Log only 1st error, till FW clear the STATUS bit") freeze the captured address/id/user fields the moment the first event sets the bit. A driver that reads STATUS + capture and never writes back produces a stream of host notifications all carrying the *first* event's payload — silently misleading, no error path. The bug-finding heuristic: in a diff that adds multiple "read capture + notify host" workers, diff their structure against each other. If one (e.g. an axi-split clear) writes back to a CLR/STATUS reg and another (e.g. axi-term read) doesn't, the second is probably wrong — go to RTL to confirm. Record the sticky-bit pattern in the per-IP knowledge base so the next review on a sibling instance lands faster. **When a *prior* review round already got this fix landed on one worker, re-check every sibling capture worker in the same PR — the fix tends to land on the exact function you anchored the comment on and not its structurally-identical twins across an intra-repo layer boundary** (e.g. the EP/controller-side reader gets the re-arm, the PIW/fabric-side reader with the same STATUS+ADDR/ID/USER shape does not). Diff the sibling workers against the one you know is correct; a missing write-back is the tell.
- **Two consumers that both read-and-W1C-clear the same sticky cause register race — and the higher-priority one wins.** When a PR adds a *synchronous* read-and-clear of a cause/status reg (to return an error code to a blocking caller) but an ISR on the same block already reads-and-clears the same reg, they compete: the ISR (interrupt priority > thread) preempts the poll and clears the cause first, so the synchronous read sees 0 and reports success — silently defeating the exact error propagation the PR adds. The tell: a `check_*_errors()`-style helper called from *both* `dma_transfer`/poll path *and* the ISR. The fix is on the interrupt side, not the sync read (the sync path genuinely needs a return value the ISR can't provide): mask the IRQ around the synchronous transfer, latch the status into device data for the sync path to read, or pick one model per instance (fully polled with IRQs off, or fully interrupt-driven with a completion sem). A happy-path sibling consumer that "works today" only proves the *non-fault* path survives the ISR — the fault/error path is the untested new window.
- **An enabled interrupt with no consumer is a liability, not a feature.** Before accepting a driver that enables its IRQs at init (because the DT node is `okay`), grep for who actually uses the async path: a registered completion callback and any `wait=false`/non-blocking caller. If nothing registers a callback and every caller is synchronous (`wait=true`), the ISR's completion branch is dead and the only *live* effect of the enabled IRQ is to read-and-clear the same cause regs the synchronous poll depends on — pure downside. Recommend not enabling the IRQs until a real async consumer exists (or masking them around synchronous transfers).
- **The CAUSE / MASK / MASKED_INTR register triplet means "masked" ≠ "invisible to a poll monitor" — so a bit deliberately masked yet still bound + drained on the poll path is coherent, not contradictory.** MASK gates only the CPU line (`MASKED_INTR = CAUSE & ~MASK`); the raw CAUSE register latches the bit regardless of MASK, and a poll-based IRQ monitor reads CAUSE directly. When a PR keeps a summary bit masked (to suppress a redundant/duplicate CPU line) but still registers a handler on it and drains the underlying leaf, verify the shape against the actual register triplet before flagging "you masked it but still handle it" — confirm which register the monitor polls and that MASK feeds only the interrupt output, not CAUSE. Record the per-IP triplet offsets/bit-positions in the IP knowledge base.
- **A handler that drains a shared leaf is idempotent across dual/duplicate summary bindings *iff* the walker clears the summary after dispatch (post-order W1C).** When one error sets two summary bits (e.g. a SEI and an SPI root both flagging the same underlying block) and the same handler is bound to both, correctness rests on ordering: the handler must clear the underlying leaf *before* the tree walker W1Cs the summary bit, so a level-driven summary has de-asserted by clear-time and doesn't retry-storm. Confirm the walker is dispatch-then-clear (not clear-then-dispatch) and that the handler reads-0/returns-"nothing-handled" on the second dispatch. Then "whichever summary is walked first drains the pair; the second is a no-op" holds order-independently — verify, don't assume.
- **On a summing IRQ-tree walker, a handler must return 0 (not a negative errno) for "not my config / nothing to do" cases.** When the dispatcher accumulates handler return codes with sticky-negative semantics, a negative return poisons the aggregate handled-count for the whole cause register (though it does *not* skip sibling handlers — they still run; only the reported count is corrupted). Reserve negative returns for genuine failures worth surfacing; a "port/die not wired to me" (`-ENOTSUP`-class) skip should return 0. The tell is an author who carefully returns 0 on the *config-absent* path but lets a manager/callee error fall straight through as negative — the two "nothing to do here" cases should be handled the same way.
- **A handler on an ISR/poll-reachable hot path should rate-limit its per-event logs — check sibling handlers for the convention.** A driver that adds rate-limited log macros "for paths reachable from an ISR on every interrupt" but then uses the plain (unbounded) variant inside the per-event success loop is the tell; a persistent/re-arming error floods the log every poll. Diff against the established sibling handler (it usually already rate-limits the same loop) and flag the inconsistency as a suggestion.

### Concurrency, Caching & Observability
- **A stateful select-then-read register viewport needs the lock its sibling in the same driver already takes — and a PR that adds a second caller is what makes the gap live.** When readout works by writing an index/selector to one register then reading companion data registers, the selector is shared mutable hardware state. Grep the driver for an existing lock around the *same* shape (RAS-DES-style event-counter viewports are the usual precedent, wrapped in `k_spin_lock(<drv>_get_*_lock(dev))` at every call site) — if one exists and the new path omits it, that asymmetry is the finding, and the in-repo precedent makes the fix uncontroversial. Severity is driven by what the PR itself adds: a new shell command alongside existing parent-device forwarders (the path a future management/middleware subsystem will use) means two genuinely concurrent readers. Interleaved index writes don't yield a stale read — they yield entries attributed to the *wrong slot*, indistinguishable from a corrupt log. Accept either a lock or a documented hard single-caller constraint, but note the lock is cheaper than the constraint.
- **Check observability before flagging a race.** If the suspected bad window produces a `LOG_WRN`, a rejection, and an error return to the caller, the failure is visible and recoverable — it may be the caller's fault, not a defect. Drop the finding.
- **A "deny/lockout after programmed" DoS gate on a public buffer-handout accessor is best-effort by design — scope-check the threat model instead of chasing the TOCTOU.** When an API stops handing out a writable pointer to shared state once a monotonic `programmed` flag flips, two reflexes are usually wrong: (a) the TOCTOU between the check and the pointer return is benign — the flag is one-way (false→true) so the read is safe outside the lock, and any handed-out pointer already outlives every lock, so a cooperative caller can't be hard-fenced anyway; (b) a pointer-returning accessor that returns NULL on mutex-timeout *and* on "invalid" *and* on "locked" can't convey an errno — that conflation is inherent to the shape, not a defect, as long as the timeout is logged. The finding that *does* matter is scope: verify the untrusted actor can't reach a sibling internal write path that mutates the same buffer. Grep the public header (the actor's surface) vs the internal header — if the single-entry `write_*_entry` mutators live only in the internal header and the bulk buffer accessors are the only public path, the lockout is coherent; if a mutator leaks into the public surface, the DoS protection has a hole.
- **Verify the actual preemption model before flagging a lost-wakeup / TOCTOU race.** A try-lock-then-release gap is only racy if a second context can run *in* that gap. Confirm the real interrupt/scheduling model (IRQ priorities, nested-vs-run-to-completion controller, ISR vs thread/workqueue) — often the converging paths are serialized (same-priority IRQs, or a controller that dispatches handlers in one loop), which precludes the race entirely. Research the interrupt controller, don't assume the textbook PLIC/NVIC nesting model from the name. If precluded, downgrade to at most a one-line invariant note ("relies on these staying serialized; re-check if moved to preemptible context").
- **Re-running idempotent config on already-configured HW is not a defect.** A reset path that reprograms a block which wasn't actually reset (e.g. WD resets the wrapper but not the controller) just rewrites the same DBI/iATU/security values — harmless. Don't flag "reconfigures live HW" as a bug unless the writes are non-idempotent or visible to an active host mid-sequence in a harmful way.
- **SW reset-manager callbacks follow the HW sequence.** PRE/POST reset callbacks fire around the actual hardware reset, so POST-phase inherently post-dates reset de-assertion — a removed `busy_wait` "settle" is replaced by a real ordering guarantee, not a guess. Pull the reset-domain table (which blocks reset under which reset type) before reasoning about "was X reset / is it safe to touch".
- **Evaluate caching tradeoffs against the fast path, not the slow path.** A small atomic cache that guards a hot MMIO path (~10–50ns/access) earns its keep across config sequences of hundreds of writes, even if it looks like overhead in isolation.
- **Correctness obligations scale with indirection.** A cache introduces a contract (every gate owner must invalidate on close). When the tradeoff is justified, document the obligation at the registration macro (e.g. `EL_DIE_GATE_DEFINE`), not just at the invalidation function.
- **A POR/cold-reset persistence flop whose reset value the boot flow already relies on is spec-zero at cold boot — don't demand magic/versioning/sanitization for it.** When persistent state (an ownership bitmap, a mode flag) lives in a register in the POR/cold-reset domain, check the register's spec reset value and reset domain in the attr header before flagging "garbage bits on first power-on." If it resets to 0 on cold reset (and often the ROM's own POR detection depends on that), there is no spurious-state risk and no need for a magic number or version field — the hardware already guarantees the clean-slate invariant. Verify against the register attr header + boot flow, then drop the sanitization finding rather than posting a defense against an impossible state.
- **Prefer reject-during-init over freezing the scheduler to serialize a claim against bring-up.** When a per-resource claim (host/manager ownership) can land mid bring-up, `k_sched_lock` only helps for the *single-threaded* init phase — it does nothing for the genuinely concurrent work that runs in a *preemptive* init thread and is gated per-op. Freezing just the safe phase while the racy phase stays exposed is asymmetric theater. The cleaner model is a `busy`/`in-progress` flag: while set, reject incoming claims with `-EBUSY`/`-EAGAIN` (retryable) so the caller backs off, instead of extending the scheduler lock across the preemptive sequence (which would defeat the very reason that work is on a thread). **The busy flag must clear on bring-up *failure* too** — don't wire it to an `initialized` flag that only sets on success, or a timed-out/aborted bring-up rejects ownership forever. Also: an internal restore/replay path (cold-flop → RAM) must *bypass* the reject gate (or use an internal setter), and the retry contract ("claims may return -EBUSY for up to ~seconds during init") should be documented at the claim API.
- **`STRUCT_SECTION_ITERABLE` + linker fragments is the clean extension pattern** for composable cross-component subsystems — compile-time registration, no runtime tables owned by a single driver. Prefer over vtable dispatch for cross-component coordination.
- **Hardcoded die ID 0 as "local" is a latent bug.** Transport wrappers comparing extracted die ID against literal 0 break on non-primary dies. Use a runtime-resolved "self" die ID (DTS or global config).
- **A per-op ownership gate that returns `-EACCES` while owned imposes a *benign-skip contract* on every orchestration call site, not just the gate.** Once a device-class API returns `-EACCES` when the system manager owns the device, callers must treat `-EACCES` as "skip, not a failure" (continue / return 0), never as a hard error behind a misleading `"init failed"` LOG_ERR — and equally must not *silently drop* the return (the inverse mistake). Audit each orchestration site's handling of the gate's sentinel; a mix of "propagate as error" and "ignore" across sibling calls in the same bring-up path is the tell. Reachability is usually runtime-only (deferred validation, shell dumps, re-config) since primary bring-up predates the ownership claim — so it's a suggestion, but the misleading error log is the concrete harm. `void`-returning facade delegators that call gated child syscalls can't propagate the child's `-EACCES` at all — folds into the same return-value-discipline point.
- **Verify ownership/gate *uniformity* by counting `*_owned_check` call sites against syscall z_impls per driver, not by eyeballing one header.** When a top-layer gate helper looks "barely used," the real coverage is at each child device-class `_api` boundary — the register access funnels through the child drivers, each of which gates every one of its own syscall z_impls. Count owned-check calls vs z_impl count per header (expect N/N; the `+1` is the helper's own definition). A low use-count at the facade layer is *expected* when the facade exposes only a few register-touching ops and everything else delegates to fully-gated children — confirm by the per-driver N/N count before flagging "incomplete coverage."

### API Design & Validation
- **When a guard is removed for a legitimate reason, audit what *else* it was silently providing.** A correct change (e.g. dropping an ownership gate so a passive diagnostic can answer while the host owns the device) can delete an unrelated guarantee that lived inside the same helper — classically, the ownership check was also the only thing returning early on `dev == NULL`. The result is an inline syscall wrapper that calls `<drv>_api_get(dev)` (which returns NULL for a NULL device) and then immediately dereferences `api->op`. Two compounding tells: the doxygen still promises `-ENODEV if dev is NULL`, and the *driver* impl genuinely implements that check — which is now **dead code**, because the wrapper faults before the call. Check whether the new ops are the *only* ones in the header making that `@retval` claim; if so, it's a contract the PR introduces and doesn't honour, not a pre-existing wart to leave alone. The fix is almost always already in the same header: find the sibling op that deliberately skips the same gate and copy its `if (!api)` guard — then note any error-code inconsistency between that precedent and the new docs so one is chosen. A parent forwarder commenting that it "leaves argument checking to the controller driver so the layers can't drift" sharpens the point rather than excusing it.
- **A "thick plugin" that copies a discriminator field verbatim needs the producer to actually set it — an unset field defaults to 0 = the first enum, silently collapsing two events into one.** When a consumer builds the host/wire message from a raw-capture struct and does `msg.cause = cap.discriminator` (or `kind`/`id`/`type`) straight through, trace back to the producer and confirm every path assigns it. A worker that fills `node`/`bit` (or address/id) but leaves the on-wire discriminator at its zero-init default makes two distinct causes (e.g. MSI vs MSI-X, read vs write, poison vs decode) report as whichever enum value is 0. No error, no log — the payload is plausible and wrong. The tell: a producer struct carries a semantic-cause field that no code path writes, plus a thin consumer that trusts it. Fix on the producer (set it from the descriptor or map from the already-present bit/index), not the consumer.
- **A runtime check that recovers a compile-time-known fact is an API-shape smell — but "make it a `BUILD_ASSERT`" only holds if the sentinel is genuinely unreachable.** Check that the impossible value can't arrive from a runtime source before proposing the compile-time form; otherwise the right fix is deleting the dead branch, not promoting it.
- **One API over an enum that mixes two classes of value still lets a caller pass the wrong class.** When a selector enum spans per-lane and common-lane (or per-instance and global) members but a single accessor takes any of them, naming and doc comments don't enforce the distinction. The contract needs a decision: reject the wrong class with `-EINVAL`, or split the enum so the type system does it. Scope the comment to the *caller-facing* contract — the internal convenience of one implementation is not the author's mistake.
- **When a second translation unit in the same driver hand-rebuilds a private helper's work, export the helper — don't make its validator public.** The tell is a new file that copies the driver's `DEV_CFG`/base-address macros, calls the raw register accessors directly, and reaches through a parent-device pointer that an existing static wrapper already hides. Making one internal validator non-static to serve the new file treats the symptom; the file still duplicates the macros and can still select the wrong mux type at a call site. Exporting the existing accessors (which derive the target from the address and own the base) removes the duplication, the manual configuration calls, and the reason the validator was exposed at all.
- **Generate-vs-verify rewrites legitimately drop the old cross-check validations.** When a build step flips from "read a committed artifact + validate its self-describing fields (image_name/size/hash) against the payload" to "generate the artifact from an upstream source," the removed field-consistency checks are not lost safety — there is nothing to cross-check once you emit the fields yourself. Confirm the integrity simply *moved to the input side*: a verified source (e.g. vendor `.fw` vs its `.sha256` sidecar) → deterministic transform → exact-size check → hash computed over the result. If that chain is intact, don't flag the deleted validations.
- **Code-gen + `dict.get(key, default)` is a silent-failure factory.** When a generator emits constants by looking each name up in a parsed input dict with a default (`.get(name, 0)`), a missing input file or a renamed upstream key produces a syntactically-valid output with the constant silently set to the default. No build error, no warning — the symptom shows up as a runtime timeout / wrong-address access far from the cause. Require an explicit allow-list / required-key check before emit: iterate every key the emit step will look up and raise on the first miss, listing all misses. Covers both "file went missing" and "upstream renamed the symbol."
- **Unused module-level lists in a generator are a planned-but-dropped filter.** A code-gen script with module-level constants like `_FOO_KEYS = [...]` that nothing imports or references usually means the author intended them as a parse-time filter but ended up flattening every assignment from every input into one dict instead. Either wire the list as the filter or delete it — don't leave dead allow-lists pretending to document intent.
- **Validate at the boundary, pick one discipline per layer.** Asymmetric validation (upper thunk does `device_is_ready()` on its own device but only NULL-checks the device it forwards to) yields ambiguous error logs and hides which layer failed. Either both layers fully validate with distinct messages, or only the boundary validates and the inner trusts.\n- **A half-validated *public* accessor is a smell \u2014 fully guard it, or demote it to the private header.** A function exposed in a public header that bounds-checks one arg (a die/index) but blindly dereferences its `dev` and out-pointer is stuck between two disciplines. Two clean fixes, pick one: (a) if it stays public, guard the pointers to match the index check it already does; or (b) \u2014 usually cleaner \u2014 move the declaration to the private header the PR likely already introduces, next to its sibling internal accessors, when its `void`+out-param shape exists only to satisfy a `CALL_IF_ENABLED`/vtable-glue call and it isn't real general-purpose API. Its non-crashing today (all callers pass a stack `&out`) makes it a suggestion, not a blocker \u2014 but the mixed discipline is the real signal.\n- **A swallowed non-sentinel error return is fragile even when currently unreachable.** A branch that explicitly handles the benign sentinel (`-EACCES` \u2192 skip) and the success case but lets *any other* negative return fall straight through to normal processing (no log, no propagate) is a latent root-cause-loss bug: today the callee only ever returns `0`/one sentinel, so it can't fire \u2014 but the day it grows a real failure return, the code proceeds to configure hardware it couldn't probe, and the failure only surfaces one step downstream with the root cause gone. Flag it for consistency when a sibling path in the same PR already does the right thing (collects `first_err` / propagates). A naive-question framing (\"if rc isn't `-EACCES` and isn't 0 you continue anyway \u2014 intentional?\") invites the author to confirm each site cheaply.
- **Identical log strings across stacked layers are a debug-time tax.** Two layers logging the same string for different conditions guarantees future misattribution. Distinct prefixes or device names cost nothing at write time.
- **API struct fields shouldn't be conditionally compiled.** A function pointer behind `#ifdef` in the struct means consumers can't safely NULL-check it. Always declare the field, assign only when the impl exists, return `-ENOSYS` at the call site when NULL.
- **Macro-result member access is a code smell.** Initializer macros ending in `,` then "chained" with `.field = ...` only compile because the comma lives inside the macro body — a fragile inversion of "the call site owns separators". Push back even when it compiles; the fix (move the comma to the call site → `MACRO(x), .field = ...`) is cheap. Validated end-to-end in practice.
- **Function rename PRs need a word-boundary grep for the old name across `.c` and `.h`.** Function-pointer table assignments (`.op = old_name,`) and forward declarations are not caught by the rename — they reference a now-undefined symbol and only fail at link time *when actually built*. If no in-tree CI target builds the affected TU (see "Green CI is not signal"), the regression rides into main. Audit: `grep -rn "\bold_name\b" --include='*.[ch]'` after every rename. Zero hits is the only acceptable answer.
- **Header declaration vs `.c` `static` definition is C99 UB and gcc-diagnoses.** A non-static declaration in a public header (`void foo(...);`) followed by a `static void foo(...)` definition in the same TU (when the .c includes the .h) is the C99 "prior external declaration followed by static definition" case — gcc warns, `-Werror` rejects. Often appears when a doxygen-doc'd helper is exposed in the header but the implementer leaves the `.c` definition `static` from before. Either drop the header declaration (preferred when no external caller exists — also flush as dead code) or remove `static` from the definition.
- **Direct call to a vendor function bypassing a documented vendor-agnostic vtable is a layering regression.** When a header explicitly documents a generic device-class API (vtable + inline wrappers, with rationale: "to add a new vendor without touching consumer code, implement the ops and register them"), a consumer that bypasses the wrapper to call the vendor-specific function — *especially* when the adjacent lines still go through the vtable — silently breaks the abstraction the codebase is paying for. Flag even when the call compiles. Fix shape: thread the new return type / new arg through the vtable op (extending the API table is the right move when the underlying behavior changes), update the vtable assignment in the vendor driver, keep consumers on the inline wrapper. Symptoms that surface this: consumer suddenly needs to `#include <vendor_driver.h>`, or two adjacent ops in the same loop have asymmetric call shapes (`generic_a(...)` then `vendor_b(...)`).
- **`CALL_IF_ENABLED` / `IF_ENABLED` collapse `#if defined(CONFIG_X)` islands** around single conditional calls — equivalent at preprocess, removes ifdef noise. Worth propagating. **Caveat — `CALL_IF_ENABLED(CFG, fn, args..., &out)` with an out-pointer leaks an implicit dependency on the caller's prior `ret` value.** When `CFG=n`, the macro expands to nothing and `*out` is never written, so the subsequent `if (ret < 0)` reads whatever the previous code left in `ret`. Today this is usually benign (prior error paths already returned, so `ret==0`), but it bakes "no intervening code may mutate `ret`" into the surrounding function. Prefer the explicit form when the helper has a return value to convey: `if (IS_ENABLED(CFG)) { ret = fn(...); if (ret < 0) return ret; }` returning `int` directly — same DCE on `CFG=n`, no caller-side stale-value contract. Reserve the out-pointer macro form for genuinely fire-and-forget helpers (no status to propagate). Often a "nice-to-have / not worth posting" call on its own — flag it when the surrounding error-handling chain is long enough that a future edit might silently mutate `ret`.
- **Casting between structurally-identical, separately-defined structs** is safe only with `BUILD_ASSERT` on sizeof and every offset — or a single definition.
- **A `dev` back-pointer stored inside `dev->data` is circular.** `data` is already reachable as `dev->data`; storing the device in it just to recover it in a callback is redundant. Register the *device* as the callback context (`void *user_data = dev`) and pull `DEV_DATA(dev)` inside — drop the field and its assignment. Keeps the device→data direction one-way.
- **Headers must be self-contained for their accessors; include-order luck masks the gap.** A header whose body calls `sys_read32`/`sys_write32` must include `<zephyr/arch/cpu.h>` (the real impls are arch-specific, e.g. `arch/riscv/sys_io.h`); `<zephyr/sys/sys_io.h>` is doc-only `@fn` stubs with no implementation. It still compiles for every TU that transitively pulls the arch header earlier, so the missing include only fails in a TU with different include order. Don't "lighten" such an include to `sys/sys_io.h` — it breaks the build.
- **`LOG_MODULE_REGISTER` is once-per-name-per-link; a second TU sharing the module uses `LOG_MODULE_DECLARE`.** Two TUs both `REGISTER`-ing the same module name = duplicate-symbol link error. The fix on a build-fix PR is always DECLARE in the joiner, REGISTER in the one owning file. A self-contradictory doxygen `@return` ("0 on success … 1 if processed successfully" on a fn that only ever returns 1/-1) is comment-is-the-bug — drop the impossible clause.
- **Handler return value: when the "did work" boolean reports work that itself is a bitmask of flags, return the executed-action mask instead of `0/1`.** A callback whose contract is "return >0 if handler took action" and whose body is `if (actions & FLAG_A) ...; if (actions & FLAG_B) ...;` gains observability for free by returning the subset of `actions` actually executed. Tests can then assert `expected_actions == returned_actions` to verify *which* branches ran, not just that *something* ran. `return actions ? 1 : 0` is the floor; `return executed_mask` is the ceiling.
- **Don't dispatch on `dev->name` (or other display-name string compares).** A function that picks which config struct to cast by `strncmp(dev->name, "some_prefix", N)` carries three latent bugs at once: (1) every call pays a string-compare cost (in ISR context this stacks), (2) any DTS label rename silently routes to the wrong cast (and the two configs are *not* shape-compatible, so subsequent field accesses return garbage with no compiler help), (3) prefix matches collide with future siblings (`some_prefix_v2`). Encode the discriminator in the cookie/handle the caller already passes, or place the discriminating field as the first member of a shared config header so a single cast works for both device kinds. Reserve symbol-name lookups for genuinely debug-only paths.
- **Don't name a state machine after one optional sub-step.** If the guarded action calls one function that does several things (some `#if`-gated, e.g. link-up only under `LINKUP_CFG`), naming the FSM `LINK_INIT_*` misleads when that step is compiled out. Name it after the whole action / its module-scoped prefix (`reset_done`/`reinit`), not the narrowest sub-step. Avoid "bring-up" for a warm re-init path — it connotes cold boot.
- **Kconfig `default y if !X` is not `depends on !X`.** A symbol that only *defaults* off when X is set can still be force-enabled alongside X, producing a silent contradiction (the symbol advertises a feature while the `#ifndef X` body skips it). If two configs are mutually exclusive in practice, encode it with `depends on`, not just a conditional default. Also watch for the same guard spelled two ways across decl vs use (`#if !X && Y` vs `#ifndef X`→`#if Y`) — easy to drift.
- **`depends on` answers "where is it safe", not "why on-by-default".** When a reviewer asks "why `default y`, not `n` + opt-in?", a `depends on FOO` reply only proves the symbol falls back to `n` where FOO is off (it becomes unselectable → `n`) — it does *not* justify auto-enabling for every config that *does* satisfy the dep. Those are orthogonal: `depends on` bounds the blast radius, `default` decides opt-in vs on-by-default *within* it. Check sibling features in the same Kconfig for the convention — if a neighbor (`*_HOST_SVC`) is bare `bool` (opt-in), a new `default y` is the outlier. Usually a suggestion, not a blocker, once the author has tested the host path.
- **Read the new symbol's own help text for the config it names — that's the `default` it should key on.** A feature added to cover a gap that another config creates (e.g. a polled check that exists because the minimal-init build excludes the interrupt-driven driver) frequently ships `default n` while its help text explicitly says "for `EL_PCIE_EP_MINIMAL_INIT` configurations that have no …". That mismatch is the finding: the author knows exactly which config needs it and still made every one of those builds opt in again, so the gap the PR was written to close stays open by default. `default y if <the config named in the help text>` is the fix, and it's stronger than a bare `default y` because it keeps the feature off everywhere the gap doesn't exist. Generalize: whenever a Kconfig's help text names a sibling symbol as the motivating case, check the `default` expression mentions it too.
- **A new feature Kconfig with no `default` and no board enabling it is a no-op gate.** When a flag-gated path has zero `=y` anywhere, the conversion is correct but inert and the code gets no compile coverage. For emulation/host-only payloads (a large embedded blob, a sim-only load path) prefer `depends on ARCH_POSIX` + `default y if ARCH_POSIX` — turns it on for the only target that wants it, off for real silicon, and self-documents intent. A dependent mechanism flag (e.g. "load via DUP") should `depends on` the master so a board can't request it and silently get nothing.
- **Gate HW-config logic on the *action* Kconfig, not the *data-availability* one.** A symbol that only pulls in descriptor/table *data* (a BAR→SoC map, a routing table) is necessary-but-not-sufficient for the code that *acts* on it (programs BMU/iATU/etc.). Gate the config logic (and its vtable slot) on the feature that expresses intent-to-configure — typically the one whose sole consumer file is already gated on it — even though the looser data flag would still compile (the action flag usually `depends on` the data flag, so it's a subset). The tell that the gate is too loose: a test/config that enables the data flag but *not* the action feature's other deps still compiles the `_impl` and wires a live vtable op the build never intends to call. Leave read/dump paths (which don't touch the descriptors) ungated. Downside of the loose gate is latent, not a crash — dead-but-live op advertised — so it's a suggestion, but the tighter gate makes the disabled slot NULL → syscall returns `-ENOTSUP`, correctly reflecting "not configured."
- **A named linker section with no placement fragment is an orphan — `Z_GENERIC_SECTION(.foo)` alone is only half the job.** Tagging a blob/array into a custom section compiles and links, but with nothing in a linker script placing `.foo` it lands at an arbitrary address and emits no boundary symbols. Code reachable only by the symbol still works; any "find it by location" consumer (a DMA/debug path sourcing alternate FW, an offline tool keyed on a fixed address) has no anchor. This is the linker analog of the no-op-gate / dead-enum family: *declared but not wired*. When a section name is the point (not just `.rodata` placement), require the matching `zephyr_linker_sources(SECTIONS …)` fragment that pins it and emits `__foo_start/_end`. Iterable registries use `ITERABLE_SECTION_ROM`; a raw blob needs the fragment hand-rolled.
- **Single-source a size constant shared by a copy loop and its bounds assert.** When the loop length lives in one TU (`for i < SIZE/4`) and the array-size `BUILD_ASSERT(sizeof(arr) == SIZE)` lives in another, the two `#define SIZE` copies are independent: bump one and the loop runs the other TU's array out of bounds (over-read) or truncates the payload (under-read), with only the local assert guarding its own value. Hoist the constant to a shared header both TUs include so the asserted size and the consuming length can't drift.
- **Runtime `__ASSERT` on a devicetree-derived value already constrained by the binding is redundant — and if placed mid-sequence, violates validate-before-mutate.** When a field comes from `DT_INST_PROP(...)` and the binding pins it (`enum: [0,1,2,3]`), the DT compiler rejects out-of-range *at build time*, so a runtime assert on the only real path can never fire. Worse, when the assert sits *after* earlier register writes in the same function, a hypothetical failure leaves the block half-programmed. Prefer a `BUILD_ASSERT` in the config macro (where the value is a compile-time constant — there's usually already a `BUILD_ASSERT` precedent in the same macro), or, if a runtime guard for non-DTS callers is genuinely wanted, hoist *all* validation above the first write. Grep for a non-DTS caller before insisting either way — if there's only the one DT path, the simplest fix is to drop the assert and lean on the `enum`.
- **A guard's redundancy is not static — adding a public entry point can retroactively justify a runtime check you'd have dropped a round earlier.** A runtime bounds-check on a `DT_INST_PROP`-derived field that was "redundant vs the binding `enum`" (only reachable via the constrained DT path) becomes *justified* the moment the same PR grows a public `__syscall`/exported API that admits non-DTS callers passing arbitrary values. On re-review, before re-raising a prior "drop this redundant validation" finding, re-check whether a new caller path appeared — if it did, waive the finding and note the guard now has a real job. Same field, opposite verdict, because the reachability changed.

### Specialized PR Types
- **A per-port/per-instance HW config-bit PR that clones an existing sibling switch reviews by diff-against-sibling, not from scratch.** When a new feature toggle (e.g. a `C2C_CFG.EBR_EN` on/off) is a faithful clone of an established one (`pos-enable`), verify the five parallel pieces line up: the DTS binding (`type: int`, `enum: [0,1]`, `default` matching the register `__RST` bit), the config-struct field, the vtable op + `__syscall` wrapper behind the same ownership guard, the RMW impl, and the shell command. Once the clone is confirmed structurally identical, spend the real attention on the *one* place the new HW differs from the sibling — here the toggle hazard — and treat everything the sibling already does the same way (out-pointer discipline, `-EACCES`-on-read, log level, dead `argc` floor check) as settled convention, not findings. Reset-default preservation is the safety proof: if the register's `__RST` value has the bit in the state the `default` reproduces, `hw_init` writing it back is a no-op and the PR is functionally inert by default.
- **A "warn but proceed" runtime guard on a destructive HW toggle is a legitimate question, not a blocker, when the init path can't reach the hazard.** When flipping a config bit mid-traffic can strand or duplicate a transaction (an AXI-protocol-level fault the peer can't recover), a shell command that only emits a `shell_warn` before doing it is worth a *question* about whether it should hard-refuse while the link is up. But first confirm the DTS/init path applies the value *before* any traffic (before port enable / PHY-FW init) — if so, the only exposed caller is the interactive debug shell, the hazard is documented in the binding + API doxygen + shell help + the warn, and the finding stays a non-gating question.
- **Project-agnostic build/tooling repo: separate stable paths from project-varying values.** Hardcoded repo/IP paths identical across projects are fine; project-varying values (product/variant sets, image sizes, memory-map base addresses) don't belong as literals — source them from a project config/header/registry. Check sibling precedent (e.g. a PCIe PHY-FW path in the same file): a value with existing precedent (size) can ride along, but net-new couplings (a variant frozenset, a source base address) have no cover and deserve the push.
- **A dense, contiguous `<address>,<data>` hex means the base is `min(addr)` — a hardcoded base constant is redundant.** Verify continuity programmatically (unique, stride-`word`, no gaps); if dense from `min`, derive the base from the file and drop the literal, and consider asserting `payload_size == expected_size` to catch a truncated/sparse vendor drop.
- **Test-infrastructure PRs need a segregation audit.** For PRs that introduce shell commands, inject APIs, record buffers, or instrumentation, walk the gating tree explicitly: (1) Is each test-only symbol behind a *test-only* Kconfig (e.g. `*_IRQ_TEST`), not just behind the broader feature Kconfig the production driver also needs? (2) Does the production ISR / fast path pay any cost for test scratch state? (3) Are record-keeping / inject helpers separated into their own TU (or `#ifdef` blocks) so the production build links nothing test-only? Partial gating — shell command guarded, supporting helpers not — is the common shape. Flag at the test-only function definition, not at the build glue.
- **Vendor SDK drops are not feature PRs.** Don't review tens of thousands of lines of vendor code line-by-line. Check: right directory? build integration (CMakeLists, Kconfig) correct? version/license header present? Is the tree pristine vs the vendor tarball (local patches belong in a separate overlay, not mixed in)? Is the version captured somewhere auditable for clean future diffs?
- **Empty-library build-warning fixes: verify the sanctioned property and that it's scoped to observed-empty libs.** A `zephyr_library()` whose sources are all added via `zephyr_library_sources_ifdef(CONFIG_… …)` becomes empty (and emits a "No SOURCES given to target" configure-time warning) in any config that sets none of those `CONFIG_*`. The correct suppressor is `zephyr_library_property(ALLOW_EMPTY TRUE)` — confirm the property/arg name against `cmake/modules/extensions.cmake` (it's a real single-arg), not an invented flag. Keep it scoped to the libraries actually observed empty; don't blanket-apply across driver dirs, since that would also silence a genuinely-misconfigured empty lib later. Build-only, zero blast radius → approve.
- **Pure data-table PRs: verify cross-repo consistency and spec cross-check.** When the same lookup table is duplicated across repos in different formats (Python dict, shell `case`, Starlark dict), diff entries against each other *and* against the hardware spec/header. The code pattern is trivially correct; the values are where bugs hide.
- **Design reviews: evaluate each pillar independently.** A multi-part proposal can be 2/3 right. Don't let disagreement on one part color the whole review. Ground every architecture argument in actual code (read the candidate files and prove generalizability or its absence with concrete evidence).
- **Repo boundary > directory convention for enforcement at scale.** With many devs, a repo boundary creates natural friction (separate CI, CODEOWNERS, release tags); subdirectory conventions rely on review discipline that degrades. When code is misplaced across a boundary, *sharpen the boundary* (move the misplaced code) rather than remove it. Heuristic: a driver that `#include`s an IP register header belongs in the corresponding `ip.` repo; otherwise it's SW infrastructure. Consider scaling (a consolidated repo grows with every product) and CI blast radius (product changes should trigger product CI).
- **Driver functional-domain file splits.** Name files after the HW concept, not borrowed SW abstractions (`bar_map`/`addr_xlat`, not `mmap`, for BAR→SoC translation). Give each domain file its own Kconfig guard; the init function calls into each via `#if defined(CONFIG_...)`. Avoid `__maybe_unused` — fix variable scoping during the split. Don't add empty `// todo` files (structure without substance). Every `#endif` in nested driver-init macros and internal headers needs a `/* CONFIG_... */` comment. Wrap always-together low-level call sequences (poison mask + MSI-X DBI + security level + response manip) into a single named helper — the name becomes documentation.
- **Defensive guards inside internal statics — keep or drop is taste.** Note redundancy when a helper's only caller already enforces a guard, but don't insist on removal; depth-in-defense has value if the helper grows new callers.
- **Avoid naming one specific transport in shared documentation.** When a subsystem can reach remote dies via more than one indirect interface (SPI-GW or side-band), comments and docs must describe the generic mechanism ("indirect interface"), not the platform's current choice. Flag every such mention.
- **Don't bind a model's vocabulary to one concrete actor/claimant either.** The same "describe the mechanism, not today's instance" rule applies to *who* acts, not just *how*. An ownership/arbitration model that names the claiming entity concretely ("host", "BMC") throughout docs/headers/comments will read wrong the day another manager (host driver, platform RAS, an OOB agent) does the claiming — the gate doesn't care who claims. Push for an abstract term ("system manager" / "management entity"). **Anchor the one comment where the concept is first *defined* (the model doc), define the canonical term there once, and ask for a sweep — rather than annotating every occurrence.** One well-placed terminology comment beats N inline dupes across headers and drivers.
- **An IP driver taking a *project* base address is a layering blocker, not a nit.** When a production driver in an `ip.*` repo `#include`s project-level base-address headers (`project_bases_fw.h`, `*_cold_flops.h`) to compute an absolute register address (`PROJECT_BASE + IP_OFFSET`), it hard-couples the IP repo to a project's address-map layout — a product that lays memory out differently won't build. The fix is to route the access through a proj_infra utility (an accessor that owns the base) or, better, a dedicated manager in the owning block (e.g. a cold-flop manager in psoc) that is the sole owner of that register class and centralizes the read/write. Confirm it's a real regression by grepping the *other* includers of the project header in the IP repo: if they're all `tests/`, `*_sv.c`, or gdb/trace/debug files, there is **no production-driver precedent** and this is the outlier. Same principle as "repo boundary > directory convention": a driver that reaches across an IP/project boundary for a register belongs behind that boundary's API.
- **Deleting the offending feature (with a tracked TODO) is a legitimate resolution to that blocker — sometimes cleaner than plumbing it through infra.** The author may first relocate the project-base access behind an infra accessor (correct), then go further and remove the whole mechanism, deferring it via `TODO(TICKET)` until the owning HW/resource-manager infra exists. Accept the phasing when the removal is documented (commit body + TODOs) and the feature stands on its own without it (here: an in-memory gate that still protects the steady-state case, only losing reset-survival). Verify the removal is complete — grep the removed symbols/includes repo-wide, and confirm dropping an include orphans no *other* symbol it provided. A storage-format `BUILD_ASSERT` dropped alongside (e.g. `packed-bitmap <= 32 bits`) is safe to remove iff it only guarded the deleted storage, not the surviving in-memory representation — check what the assert actually bounded before clearing the "they removed a safety assert" reflex.
- **Bare `TODO:` deferrals should be promoted to the same-file tracked form.** When a phasing decision leaves `TODO:` comments and the file already uses `TODO(TICKET):` two lines away, flag the inconsistency as a one-line nit — reference the ticket that owns the deferred work so it's greppable against the tracker. Cheap, non-gating, and backed by the file's own precedent.
- **The sanctioned fix for that blocker is an `el_dev_utils`-style infra accessor — and infra including `project_bases_fw.h` is NOT the same violation.** When the layering blocker is resolved by moving the base ownership into a generic `module.infra` dev-utils accessor (`el_dev_utils_cold_flop_read/write(offset)` that owns the block base and does the `sys_read32/write32`), don't re-flag the fact that *infra* now includes `project_bases_fw.h`. That header is a build-generated per-arch base header resolved via include-path, and `el_dev_utils` is the layer designed to absorb it — the sibling `el_dev_utils_strap.c` already includes it and owns a project base behind an accessor. Verify by grepping for that sibling precedent in the same dir; if it exists, the fix is idiomatic (base owned by infra, slot allocation owned by `proj_infra`'s central `*_cold_flops.h`, IP driver names only its slot). The coupling didn't relocate to a new wrong place — it moved to the place that already owns it.
- **Compile-coverage check on DT-instance macros.** Init macros gated by `DT_INST_FOREACH_STATUS_OKAY` only compile if some CI config enables that instance. When raising shape concerns about such a macro, also ask whether any CI build actually instantiates it.
- **Green CI is not signal when no config builds the changed code.** Before trusting a green PR, locate at least one in-tree CI target that compiles the touched file with the relevant `CONFIG_X=y`. The standard loophole: an in-repo `samples/build_sanity/` enables the feature flag but is *explicitly skipped* in the CI starfile ("covered by downstream apps"), and downstream apps don't enable it either — the gate is empty in both directions. Twister-skipping samples (no `sample.yaml`) and unit tests that set the same flag `=n` produce the same vacuum. When a PR renames symbols, changes header signatures, or touches a vendor-driver vtable that no CI config exercises, do a local `west build` of any sample that sets the flag before approving — green checks alone prove nothing. Raise the coverage gap as a RAID/process item, not just a per-PR comment. **"Fix build errors" PRs on a gated/uncompiled TU are the canonical case** — bitrot accumulates in a default-`n` file (de-static a now-cross-TU helper, REGISTER→DECLARE a shared log module, add a missing header include); CI stays green because no `=y` sample/test/board ever feeds the file to the compiler. Verify the fixes by building the gated path locally, and flag the empty gate (no `CONFIG_X=y` anywhere) as the real defect.
- **A feature can span two TUs behind two different Kconfigs — closing coverage on one doesn't cover the other.** When the driver/vtable side is gated by `CONFIG_A` and the call-site/behavioral side by `CONFIG_B`, a sample enabling `CONFIG_A=y` compiles the driver (so a `void`→`int` signature break would be caught) while the loop that actually consumes the return value stays uncompiled because no sample sets `CONFIG_B=y`. Green CI on the driver half is real signal; the call-site half is still a vacuum. Grep *both* flags before concluding the fix is CI-covered, and scope the RAID note to the still-uncovered TU rather than claiming the whole feature is exercised.
